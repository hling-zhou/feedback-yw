# 工单五字段生成规则

**版本**：2026-09-05  
**读者**：产品、运营、开发（看「怎么来的」，不是改标签库操作手册）  
**实现入口**：`src/lib/ticketAnalysis/ticketAnalysis.js`（规则初标）→ ticket LLM 增强 → `tagTicketDimensions` / post-LLM 维度重打

五个字段不是一次生成。流水线是：**先抽请求内容 → 再挖痛点 → 再用二者打三个标签**。

| 字段 | 记录键 | 形态 | 谁生成 |
|------|--------|------|--------|
| 请求内容 | `customerRequest` | 自由文本 | 规则抽取 + 可选 LLM 精炼 |
| 痛点 | `painPoint` | 自由文本 | 规则改写 + 可选 LLM 挖本质 |
| 请求场景 | `requestScene` | 全产品共用标签 | 决策树（LLM 不直接分类） |
| 问题类型 | `problemType` | 全产品共用标签 | 决策树（LLM 不直接分类） |
| 用户旅程 | `journeyL1` / `journeyL2` | 按产品标签 | 关键词打分（LLM 不直接分类） |

规则层实现细节（候选 phase、截断常量、测试命令）见 [TICKET-ANALYSIS-P0-RULES.md](./TICKET-ANALYSIS-P0-RULES.md)。

## 1. 总顺序

```
工单原文（受理 / 追加 / 处理 / 客户原话）
    │
    ├─ 1. 请求内容  customerRequestExtract → 可选 LLM
    ├─ 2. 痛点      painPointExtract（主输入=请求内容）→ 可选 LLM
    └─ 3. 三标签    语料 = 请求 + 痛点（空则回退受理/追加/处理意见）
         ├─ 请求场景  requestSceneClassifier（9 类，命中即停）
         ├─ 问题类型  problemTypeClassifier（12 类，命中即停）
         └─ 用户旅程  matchJourneyByDescription（当前产品旅程树）
```

打标语料：`buildDimensionTaggingText` 优先拼接 `customerRequest` + `painPoint`；都空时才用受理+追加（主）/ 处理意见（辅）。

人工改过的标签默认不覆盖（`manualTagFields`）。ticket LLM 成功写出请求或痛点后，默认按新语料重打请求场景和问题类型（设置里可关）。

## 2. 请求内容（`customerRequest`）

**目标：** 客户想做什么、遇到什么问题。不写解决方案、处理意见、平台结论。

### 规则层

1. 从全生命周期收候选：客户原话 → 受理/追加字段（客户问题、详细内容、工单标题等）→ 协办/反馈里的客户表述 → 处理意见里像客户诉求的句子。
2. 过滤：占位空文、内部流转话术、平台结论（如「客户未提供信息」「离线处理」）、格式化模板、不像诉求的句子。
3. 多条时合并或择优：
   - 明确修正（「之前说的不对 / 其实是」）优先
   - 已解决且无故障词的降权
   - 严重性：故障 > 性能 > 咨询 > 其他
   - 再比出现顺序、完整度
4. 截断：1～3 句，默认 ≤80 字，硬上限 120 字。

### LLM 层（配置了大模型时）

- 综合各环节，不是照搬首次原话。
- 优先级与规则一致：修正 > 严重性 > 最新未解决 > 最完整。
- 删情绪词和内部话术；保留时间、频次、资源类型。
- 禁止写入「解决方案 / 处理意见 / 问题原因」和平台回单口径。
- 校验失败则回退规则结果。

主要代码：`src/lib/ticketAnalysis/customerRequestExtract.js`、`customerRequestLLM.js`、`ticketAnalysisUnifiedLLM.js`。

## 3. 痛点（`painPoint`）

**目标：** 比请求更本质一层的客观陈述，不得与请求矛盾。禁止「用户希望/建议/反馈/要求」开头。

### 规则层

1. 有请求内容：先去掉「用户希望/建议…」等引导语，再按模板改写（如「希望批量删除」→「删除资源需逐个操作，效率低。」）。
2. 否则依次试：`客户反馈…` / `故障现象` / `问题现象` → 根因列或「定位为 / 经排查」且含客观词（无法、失败、不通等）→ 工单标题。
3. 去掉纯情绪词（真无语、烦死了、催、尽快…），保留程度（非常慢、持续卡顿）。
4. 最长 80 字，尽量收成一句并补句号。

### LLM 层

- 主输入是请求内容，正文为辅，根因仅参考。
- 写问题本质，不写表面操作；需求类改成客观陈述。
- 不合格（太短、仍以「用户希望」开头等）则回退规则结果。

主要代码：`src/lib/ticketAnalysis/painPointExtract.js`、`painPointLLM.js`。

## 4. 请求场景（`requestScene`）

**性质：** 全产品共用 9 类。按决策树**从上到下，命中即停**（复合场景取第一个）。无命中默认 **产品信息咨询**。

定义与优先级：`src/lib/sharedTagDefs.js` 的 `REQUEST_SCENES_BUILTIN`。判定：`src/lib/requestSceneClassifier.js`。

| 优先级 | 标签 | 判定要点 |
|--------|------|----------|
| 1 | 报障与排错 | 不通、中断、报错、故障、无法访问、卡顿/慢等；「为什么慢」且无故障词不算；开通/退订失败不算 |
| 2 | 资源操作申请 | 申请配额/扩容/解售罄/开通权限，或退订释放且非「怎么退订」；操作失败+开通类动词也算 |
| 3 | 操作指导 | 「如何/怎么」或步骤/教程；绑定解绑修改且无失败词 |
| 4 | 进度催办与协同 | 催办、进度、还没好、建群协查；带投诉/赔偿的让给申诉 |
| 5 | 产品信息咨询 | 是否支持、规格、价格、区别；「怎么提升配额」且未说「请提升」 |
| 6 | 方案咨询与设计 | 方案、架构、选型、迁移、割接、组网 |
| 7 | 费用与账务 | 账单、扣费、退款、多扣少扣；纯问「怎么收费」且无异常不算 |
| 8 | 信息查询 | 查有效期/备案/归属/配额等，且无催办 |
| 9 | 服务申诉与投诉 | 投诉、态度差、要求赔偿、督办 |

打标时：先用请求+痛点；未识别再用处理意见；仍空则用路径节点兜底。

业务规范（若仓库内有）：`data/请求场景标签体系及打标规则.md`。

## 5. 问题类型（`problemType`）

**性质：** 全产品共用 12 类。同样**按表顺序命中即停**。未命中 → **其他**。

定义与优先级：`PROBLEM_TYPES_BUILTIN`。判定：`src/lib/problemTypeClassifier.js`。决策树未中时，再用标签库关键词/说明打分兜底（`resolveProblemTypeFromConfig`）。

**前置排除：** 全文同时出现「ping 通 / 网络正常」和「对端拒绝 / reset / refused」→ 直接标 **产品功能咨询**（对端问题，不归本产品故障）。

| 优先级 | 标签 | 判定要点 |
|--------|------|----------|
| 1 | 可用性/连通性故障 | 不通、中断、崩溃、封堵、黑洞、ping 不通 |
| 2 | 性能问题 | 慢、卡顿、延迟、丢包；开通/创建过程超时不算（归开通） |
| 3 | 计费与账单 | 多扣少扣、账单错误；欠费后异常/限速也算；单纯问计费规则不算 |
| 4 | 配额与权限申请 | 申请提升配额/解售罄/灰度/8:1/订购权限/配额不足；「如何申请配额」算咨询；单纯「申请调整带宽」不算 |
| 5 | 资源开通与创建 | 创建/开通/订购失败、开通超时 |
| 6 | 配置与操作 | 绑定/解绑/改配置失败；「怎么绑定」且无失败不算 |
| 7 | 退订与释放 | 无法退订、请帮我退订；「怎么退订」且无失败不算 |
| 8 | 界面与操作易用性 | 控制台难用、按钮难找、提示不清 |
| 9 | 产品功能需求 | 希望/建议增加功能 |
| 10 | 产品功能咨询 | 如何/怎么/是否支持；或咨询意图且无操作失败 |
| 11 | 人工服务与流程 | 客服、催办、态度、故障报告 |
| 12 | 其他 | 无技术词的纯情绪，或以上都未命中 |

路径兜底仅在结果是「其他」或无法识别时启用。

业务规范（若仓库内有）：`data/问题类型自动化分类（问题类型分类与判定规则）.md`。

## 6. 用户旅程（`journeyL1` / `journeyL2`）

**性质：** **按产品**，不是全产品一套。库在各产品「用户旅程」里（Excel / 标签库），含一级、二级、关键词、说明。

打标按**客户使用该产品的生命周期**（认知/选型 → 开通/配额 → 绑定配置 → 业务使用 → 变更 → 退订）。EIP / SLB / 云专线 **不设「故障与应急」**。旅程语料只用客户请求（空则痛点），去掉联系时间/资源 ID；金牌模板、OP 前置授权、仅工单号 → 无法识别，不回退处理意见。有慢/不通/超时/丢包等产品问题时，「服务与体验」−8。报障时咨询/绑定/带宽/开通/监听除非明确在申请或改配置，否则减分，优先使用/运行侧。

### 匹配

1. 对当前产品每个二级环节打分：二级关键词命中 +3，说明里的中文词命中 +1，一级说明片段命中 +1。
2. 若客户在申请放开限制（问题类型是「配额与权限申请」，或正文含配额/售罄/轻载/灰度/订购权限等），数量配额和灰度/订购权限分开打：
   - 数量配额：提升配额、上限、IP/实例/条数 → EIP/VPC/云组网「配额与数量」，NAT「配额与实例数」，VPN「配额与规格申请」，SLB/监控「配额与权限申请」。
   - 灰度/订购权限：灰度、轻载、8:1、大带宽权限、解售罄、订购权限、上架 → 「灰度与订购权限」（SLB 上架仍可落「产品上架与交付」）。
   - 带宽升降配 −3；有「申请/灰度」时可用区选择 −8；创建/订购节点 −3，避免资源池、带宽、开通词抢走。
3. 二级互抢：同时有打不开/无法访问/时通时断和慢/卡顿（且无丢包/延迟/抖动）→ 公网访问不通，质量留给明确劣化。收取带宽配额/出账且未申请提升 → 计费，不进开通配额。专线有下单/订购/地域改不了/接入节点且无不通 → 开通与交付。
4. 取分最高的一级+二级；0 分 → 「无法识别」。
5. EIP 且 0 分时，还有一层产品关键词兜底。
6. 内容模糊（语料太短 / 标签空）→ 强制无法识别。
7. 可选：正文匹配失败时，用工单「请求节点 / 系统路径」映射旅程（设置里可关）。

先打问题类型；配额类用上述加权重匹配旅程，不再只认名字里有「配额」两个字。

主要代码：`src/lib/ticketTagging.js`（`matchJourneyByDescription`）、`src/lib/ticketAnalysis/ticketDimensionTagging.js`。

## 7. 对照

| 字段 | 规则 | LLM | 是否标签库 |
|------|------|-----|------------|
| 请求内容 | 候选抽取 + 择优 | 可精炼，失败回退规则 | 否，自由文本 |
| 痛点 | 从请求改写 / 现象 / 根因 | 可挖本质，失败回退规则 | 否，自由文本 |
| 请求场景 | 9 类决策树 | 不直接分类；只提供语料后重打 | 是，全产品共用 |
| 问题类型 | 12 类决策树 + 对端排除 | 同上 | 是，全产品共用 |
| 用户旅程 | 产品旅程关键词打分 | 不直接分类 | 是，按产品 |
