## 一、Bug 排查结论（3 个，全部定位到根因）

### Bug 1：翻页后勾选态被错误继承

**现象**：首页勾选某客户的产品部回溯复选框后翻页，新页面对应行的复选框莫名被勾上。

**根因**：`PostUseCallbackProcessModal.jsx` 的 `questionnaireSpan` / `questionnaireGroupKeys` 是**全量 dataSource 的 index → rowSpan/组 keys 映射**（第 223-240 行，基于 `questionnaireRows` 全量数组计算），但 antd Table 分页后**传给 render 的第三个参数 `index` 是"当前页内的索引"**（antd v6 分页先在 `InternalTable.pageData` 做 `mergedData.slice((current-1)*pageSize, current*pageSize)` 切片，再传给 `@rc-component/table` 的 Body；`useFlattenRecords` 对切片后的 `data` 重新 `map((item, index) => ...)`，`Cell` 调 `render(value, record, renderIndex)` 用的就是这个**页内 index**——已在 antd v6.4.2 源码中逐层验证）。

而 `mergedFlagColumn`（第 248-273 行）与"产品部溯源经办人"列（第 324-359 行）的 render 都直接拿这个页内 index 去查全量数组：

```js
render: (_v, _row, index) => {
  const span = questionnaireSpan[index]      // ← 页内 index，却查全量数组的映射
  if (span === 0) return { children: '', props: { rowSpan: 0 } }
  const keys = questionnaireGroupKeys[index] || []   // ← 同样错位
  const checkedList = keys.map((k) => Boolean(decisionOf(decisions, k)[flag]))
  ...
}
```

**后果**：翻到第 2 页时，页内 index 0-7 被拿去查全量数组的 index 0-7（即首页那批客户）→ 首页客户的勾选态/合并单元格/经办人 Select 被原样渲染到第 2 页的行上——这就是"勾选态被错误继承"的直接来源。同时也解释了为什么经办人列在非首页也会显示首页客户的经办人。注意 `rowSpan` 用错位 index 还会产生跨行合并错乱（某行 span=0 时整行单元格被吞掉）。

**修复方案（方案 A：查表改为按 row 自取，不依赖 index）**：

render 的第二个参数 `row` 就是当前行数据本身。改为给 `questionnaireRows` 的每行**预挂**分组信息（挂到行对象上，而不是靠外部 index 映射）：

```js
// questionnaireRows useMemo 中，按客户分组后，给组内每行写入：
//   row.__groupKeys = 该客户所有产品的 itemKey 列表
//   row.__isGroupFirst = 是否该客户首行（rowSpan 起点）
//   row.__groupSpan = 组行数
```

**【2026-11-04 23:00 用户拍板：操作列行级独立】** 用户质疑"一个客户下若分多个产品，不是每个产品分别指定经办人和创建回溯么？弹性公网IP和共享带宽产品被（合并）了"——确认业务语义：**产品部回溯是产品维度的动作，不同产品线归不同经办人**。原代码把操作列（勾选/经办人）也做客户级 rowSpan 合并，强制同客户所有产品共用一个经办人、一锅端归档，业务上站不住。列渲染分工定稿：

- **显示列**（客户名称/客户编码/建议触发类型）：**保留客户级合并**——render 按 `row.__isGroupFirst/row.__groupSpan` 返回 rowSpan（替代原 `mergedCell(value, index)` 的 index 查表）；
- **"客服部回访"勾选列**：**保留客户级合并**（回访对象是客户，一勾全选是既有便捷语义，用户未质疑）——render 按 `row.__groupKeys` 做 all/indeterminate + `persistDecisionsBatch` 批量持久化；
- **"产品部回溯"勾选列 + "产品部溯源经办人"列**：**行级独立**（每行 = 客户×产品，不做 rowSpan）：
  ```js
  // 产品部回溯列（行级）
  render: (_v, row) => (
    <Checkbox
      checked={Boolean(decisionOf(decisions, row.itemKey).needInternalTrace)}
      disabled={!canEdit || savingKey === row.itemKey}
      onChange={(e) => persistDecision(row.itemKey, row.sourceType, { needInternalTrace: e.target.checked })}
    />
  )
  // 经办人列（行级）：assigneeOverrides.get(row.itemKey) 独立读写，不再整组批量写
  ```

**收益**：①不同产品不同经办人的业务场景被正确表达；②归档天然逐行（客户×产品）进行，"部分归档时合并单元格不可编辑"的边界问题**从根上消失**（批判性审查发现的该缺陷随行级化消除，Bug3 渲染不再需要组级"已纳入（部分）"Tag）；③翻页 index 错位修复与业务语义修正一次完成；④旧 decisions 数据按 itemKey 独立存储，与行级渲染天然兼容，**无需迁移**。

翻页后每行自带正确分组/行级状态，页内/全量 index 错位问题彻底消除；旧的两个 useMemo（questionnaireSpan/questionnaireGroupKeys）删除前先 Grep 确认无其他消费方。

**为什么按 row 取而不是按 rowKey 反查**：rowKey 函数是 `row.itemKey || \`${row.customerCode}-${row.productName}\``，可以反查，但行对象上直接挂字段更简单、无重复计算，且与现有 `questionnaireSpan` 的语义一致（只是把"按 index 查"换成"行自带"）。

**验证方式**：现有交互无 vitest 覆盖该弹窗。修复后需人工验证：首页勾选客户 A 的产品部回溯 → 翻页 → 第 2 页行复选框全部初始未勾选、合并单元格正常。可加一个渲染冒烟测试（jsdom，翻页后断言第 2 页首行 checkbox 不勾选），参照 `Actions.render.test.jsx` 的 context mock 手法。

### Bug 2：非首页勾选后归档，提示成功但实际未纳入

**现象**：翻到非首页勾选，点"存档「产品部溯源」"，toast 提示成功，但反馈库-产品部溯源列表里没有这些条目。

**根因（与 Bug 1 同源，index 错位的另一种表现）**：

`archiveTrace`（第 437-480 行）调 `collectFollowupExportRows(recommendations, callbackNonTenRecords, decisions, 'needInternalTrace')`——**这个函数本身是对的**（`callbackFollowupTables.js` 第 94-106 行：遍历**全量** recommendations/callbackItems，用 itemKey 查 decisions map 勾选态），不翻页也不受影响。

真正的问题在**勾选写入阶段**：非首页勾选复选框时，`mergedFlagColumn` 的 onChange 走 `persistDecisionsBatch(keys, 'questionnaire', { [flag]: checked })`，其中 `keys = questionnaireGroupKeys[index] || []`——**用页内 index 查到的可能是首页某客户的 keys**！于是你在第 2 页勾选"客户 B"，实际被勾进 decisions 的是"首页客户 A"的 itemKey。归档时 `collectFollowupExportRows` 按错误的勾选状态取行，取到的是首页客户 A 的行（如果首页那行恰好已指定经办人）或干脆取空。

**toast 提示成功**是因为 `archivePostUseJiraItems(rows.map(...))` 只要有 rows（错误行）就 POST 成功返回，`message.success('已存档 N 条...')` 照常弹出——存的是错的人，或者存了 0 条也提示成功（`saved?.items?.length || rows.length`，rows 为空时走 0 条仍然 success 分支？否——`if (!rows.length) return message.info(...)` 会拦截空 rows；所以是"存了错的人"）。用户去反馈库看，找不到自己刚勾选的非首页客户 → "非首页的项都未成功纳入"。

**次要放大器**：经办人 Select 同样用错位 index 渲染（`assigneeOverrides.get(firstKey)`，firstKey 来自错位的 keys[0]），非首页选经办人时写入的也是错误 itemKey 的 override；`archiveTrace` 的"未指定经办人"校验 `rows.filter((row) => !assigneeOverrides.get(row.itemKey)?.id)` 对非首页行恒为"未指定"→ 要么被校验拦住提示 warning，要么侥幸通过但归档 payload 的 assigneeId 为空。

**修复方案**：随 Bug 1 一并修复——keys 从 `row.__groupKeys` 取，勾选/经办人/归档全链路就都正确了。单独修复勾选写入（不改渲染）也可行，但没有意义，因为渲染错位不修，用户看到的勾选态本身就是错的。

### Bug 3：归档成功后勾选保留 + 经办人被清空（预期：显示"已纳入"+经办人只读）

**现象与预期**：
- 现状：归档成功 → `setAssigneeOverrides(() => new Map())`（第 474 行）清空经办人 → 表格上勾选框还勾着（decisions 没动），经办人列变回空 Select。
- 预期：归档到产品部回溯后，"产品部回溯"列显示"已纳入"标签（无勾选框），经办人显示归档时的经办人（**不可编辑**）。若在 反馈库-用后即评满意度-产品部回溯 中删除该条目，清单弹窗对应行**回到初始态**（复选框恢复且未勾选、经办人清空）。

**根因**：
1. 归档成功只做了"清经办人"，没有把"已归档"状态渲染到行上——decisions map 与 post_use_jira_items 表是两套存储，归档动作**不写 decisions**（post_use_jira_items 按 itemKey upsert，但弹窗不知道哪些 itemKey 已归档）。
2. 没有从 post_use_jira_items 读取"已纳入"状态的任何逻辑。

**修复方案（状态联动设计）**：

**数据层**：
- 弹窗打开时（`useEffect [open]`，与现有 `listPostUseCallbackDecisions` 并列）追加一次 `listPostUseJiraItems({ limit: -1 })` → 得到已归档条目 `archivedItems: Map<itemKey, {assigneeName}>`（含已归档 itemKey 集合 archivedKeys + 各条归档时经办人）。
  - **⚠️ 批判性审查修正（23:00）**：原稿写 `limit: 0` 有 bug——仓库 `postUseJiraRepository.list` 第 154 行 `Number(query.limit) || 100`，`Number(0)||100`=100，**传 0 实际只拿 100 条**；正确写法是 `limit: -1`（truthy，走到 `rawLimit <= 0 → limit = filtered.length` 全量分支）。归档条目超 100 时旧写法会漏判"已纳入"。
- 归档成功回调里：把 `listPostUseJiraItems({ limit: -1 })` 重新拉一遍刷新 archivedKeys/archivedItems（**不乐观更新**——重新拉取同时天然覆盖"归档期间他人删除"等竞态，且与删除联动的"重开弹窗恢复初始态"逻辑一致）。归档成功后**不再清空 assigneeOverrides 中已归档行**（行级化后经办人按 itemKey 独立，未归档行的经办人选择不受影响，无需整体清空；已归档行不再渲染 Select，override 自然失效）。
- 刷新时机还有一层：弹窗常开期间用户可能去反馈库删除条目再回来。**方案**：`Modal` 有 `destroyOnClose`，每次重新打开都会重新拉 decisions + jira items，天然满足"删除后回到初始态"的需求（关闭弹窗→去反馈库删除→重新打开弹窗 → archivedKeys 不含该 itemKey → 恢复复选框且未勾选、经办人清空——经办人是 assigneeOverrides 本地 state，重开弹窗即重置）。**不需要**轮询或跨页面事件。

**渲染层（questionnaire tab 的"产品部回溯"列 + 经办人列，行级独立版）**：
```js
// 产品部回溯列（行级，每行 = 客户×产品）
render: (_v, row) => {
  if (archivedKeys.has(row.itemKey)) {
    return <Tag color="blue">已纳入</Tag>   // 行级判定，无"部分"态
  }
  return (
    <Checkbox
      checked={Boolean(decisionOf(decisions, row.itemKey).needInternalTrace)}
      disabled={!canEdit || savingKey === row.itemKey}
      onChange={(e) => persistDecision(row.itemKey, row.sourceType, { needInternalTrace: e.target.checked })}
    />
  )
}
// 经办人列（行级）
render: (_v, row) => {
  if (archivedKeys.has(row.itemKey)) {
    const info = archivedItems.get(row.itemKey)
    return info?.assigneeName || '—'        // 只读文本，不可编辑
  }
  if (!decisionOf(decisions, row.itemKey).needInternalTrace) return '—'
  const current = assigneeOverrides.get(row.itemKey)
  return <Select ... onChange 只写 row.itemKey 单键 ... />
}
```
- **行级化后不存在组级"已纳入（部分）"Tag**：每行独立判定归档与否，一勾一档一经办人，语义干净。
- **存档按钮的 rows 收集**：已纳入 itemKey 跳过（调用侧 `rows.filter((row) => !archivedKeys.has(row.itemKey))`）。
- **归档前经办人校验**：行级化后校验也更精确——`rows.filter((row) => !assigneeOverrides.get(row.itemKey)?.id)` 逐行要求，缺失清单按行报（客户×产品粒度）。
- **导出/发送待回访**等其它按钮：`needCustomerVisit`（客服部回访，客户级合并保留）与归档无关，行为保持不变。
- **权限**：`canEdit=false` 的只读用户同样能看到"已纳入"标签（本来就不能勾选，展示逻辑一致）。

**与"归档到产品部回溯，提示成功后，页面上勾选保留了"的对照**：预期实现后，归档成功 → 该组"产品部回溯"列从复选框变为"已纳入"Tag（不再有勾选框）；"客服部回访"列**保留原勾选**（该维度与归档无关，勾选状态仍由 decisions 持久化控制——这符合"勾选会保存"的产品语义）。

**经办人信息显示（不可编辑）的数据来源注意**：现有 `archiveTrace` 提交的 payload 含 `assigneeId/assigneeName`，服务端 `archiveMany` upsert 时会保留。所以从 `listPostUseJiraItems` 读回的 `assigneeName` 就是归档时指定的经办人，直接展示即可，无需另存。

## 二、新需求设计方案

### 需求 4：归档后快捷跳转到 反馈库-用后即评满意度-产品部回溯

**两个候选方案对比**：

| 维度 | 方案 A：归档成功提示中加跳转 | 方案 B：弹窗内常驻快捷入口 |
|---|---|---|
| 交互路径 | 归档成功 toast 内点"查看已归档"链接，`navigate` 跳转 | 弹窗 footer/头部常驻一个"查看产品部回溯清单"按钮，随时可跳 |
| 触发时机 | 仅归档后那一刻（toast 停留期间） | 任何时刻（包括未归档时先去看历史归档） |
| 实现复杂度 | antd message 支持 ReactNode content，配 `<Link>`/navigate 即可；toast 会自动消失（默认 3s），用户错过就没有了 | 按钮常驻，需要 new prop 从 DashboardView 传 `navigate`（或用 `useNavigate`——弹窗在 Router 内可直接用） |
| 打断性 | 低（toast 内嵌链接不打断当前操作流） | 低（按钮放在弹窗底部操作区，与现有按钮并列） |
| 覆盖场景 | 只覆盖"归档后想立即核对" | 覆盖"归档后核对 + 平时查看历史归档" |

**推荐：方案 B（弹窗内常驻快捷入口）为主，方案 A（成功提示内跳转）为辅，两者叠加成本极低**：

- **方案 B 落地**：在 `PostUseCallbackProcessModal` 底部操作区（`<Space wrap>` 里"存档「产品部回溯」"按钮旁）加一个 `Button`（icon 用 `LinkOutlined` 或 `RightOutlined`，文案"查看产品部回溯"）。跳转目标：`/feedbacks?lane=post_use&source=post_use_rating&view=trace`（已验证 `resolveFeedbackLane`/`resolvePostUseLaneView` 支持这三个参数，`buildFeedbacksUrl` 的 `stringFields` 不含 view/lane，需手拼或小扩展——直接 `navigate('/feedbacks?lane=post_use&view=trace&source=post_use_rating')` 即可）。点击后**先 `onClose()` 关弹窗再跳转**（避免弹窗残留在新页面 z-index 下）。注意跳转后的周期：反馈库页面有自己的 `InsightPeriodPicker`（周期选择独立于工作台），跳转时**不带周期参数**（URL 无周期参数时页面用默认周期，用户可在页面内自选）——如需周期对齐可后续增强，不在本次范围。
- **方案 A 落地**：`message.success` 的 content 改为 `ReactNode`：
  ```jsx
  message.success({
    content: (
      <span>
        已存档 N 条到「反馈库 · 用后即评满意度 · 产品部回溯」
        <Button type="link" size="small" className="!px-1" onClick={() => { onClose(); navigate(...) }}>立即查看</Button>
      </span>
    ),
    duration: 6,  // 稍延长给用户反应时间
  })
  ```
- **弹窗内使用 `useNavigate` 可行性**：`PostUseCallbackProcessModal` 挂在 `PostUseRatingDashboardView`（App Router 树内），`useNavigate()` 可直接调用，无需 new prop。已验证 Feedbacks 页面路由是 `/feedbacks`（App 路由注册）。

**决策点（待用户拍板）**：两方案都做 / 只做 B / 只做 A。

> **【2026-11-04 用户已拍板：两方案都做】**——toast 内"立即查看"跳转 + 弹窗内常驻"查看产品部回溯"入口，均落地。

### 需求 5：客户与证据列表在季度/年度视图下增加"数据月份"标签

**现状**：`PostUseStoryView.jsx` 第 388-425 行"客户与证据"卡片（`LimitedTable dataSource={drivers.customers}`）没有数据月份列。`buildCustomerInsights`（insights.js 第 394-434 行）聚合时**丢弃了月份信息**（`g.rows` 收集了 record，但输出对象只含 nonTenCount/avgScore/products 等，未输出月份集合）。

**方案**：
1. **数据层**：`buildCustomerInsights` 输出对象追加 `importMonths: [...new Set(g.rows.map((r) => r.month))].filter(Boolean).sort()`（`normalizedRecord` 已提取 `month` 字段，直接可用；visit-only 组没有 rows，月份为空数组）。同步更新返回类型 JSDoc。
2. **渲染层**：`PostUseStoryView` 客户与证据表加一列：
   ```js
   { title: '数据月份', dataIndex: 'importMonths', width: 130, render: (v) => (v || []).join('、') || '—' },
   ```
   放在"涉及产品"列后。**是否仅季度/年度显示**：月视图单月时该列恒为单值，展示冗余但无害。建议：**始终显示**（实现简单、口径一致；月视图下该列就是当月，用户可直观确认）。若用户偏好"月视图隐藏该列"，可在 `PostUseStoryView` 里用 `model.scope.isMonthPeriod`（storyModel 已输出该字段，第 398 行）条件拼列，成本同样很低。

> **【2026-11-04 用户已拍板：始终显示】**——不分视图粒度，月/季/年都显示数据月份列。

### 需求 7：负面反馈排除词补充 3 个

**词**：`业务使用完毕无后续使用需求`（已在！见下）、`不使用了`、`不用了`。

**【2026-11-04 新增排查：为什么占位词在集合里仍被判"负面反馈"】**

用户反馈：清单里出现"建议触发类型=负面反馈"，但具体负面反馈写的是"无/不涉及"或"业务使用完毕无后续使用需求"。已在**真实库（51,981 条用后即评记录，其中官网评分类+选项类 48,812 条）**上跑诊断脚本定量验证，根因**不是**占位词失效，而是两层叠加：

**根因 1（主因）：分号拼接串逃过整词精确匹配。**
导入解析时三个"客户回答"列的文本会**原样保留**（`parseChannels.js` 第 210-214 行不拆分号）。当一格填了多选，如 `其他;业务使用完毕无后续使用需求`，判定链 `recordHasNegativeFeedback` → `getFeedbackReasonValues` → 对**整串**调 `isSubstantiveFeedbackReason` → 整串不在占位词集合里（`Set.has('其他;业务使用完毕无后续使用需求')` = false）→ 落到 sentiment 兜底 → sentiment 把"后续"命中 `NEUTRAL_PENDING` 词表（sentiment.js 第 45 行含"后续"）判为 `neutral_pending` ≠ positive → 整串按实质负面处理。**而拆开逐片判定**（`splitFeedbackReasonPieces` 后每片 `其他`/`业务使用完毕无后续使用需求` 都在占位词集合里，应为 false）——即：**判定函数对"分号拼接串"没有先拆分再判**，而 `splitFeedbackReasonPieces` 函数已存在（reasonTaxonomy.js 第 102 行）且有测试，只是 `recordHasNegativeFeedback` 没用它。
- 实测数据：`其他;业务使用完毕无后续使用需求` 整串判负=true、拆片=[false,false]、sentiment=neutral_pending。库中共 10 条记录命中此模式（6 条"其他;…"+4 条"…;其他"），全部是 10 分记录（被"重点关注/负面反馈"路径拉进清单）。
- 同类拼接串还有：`购买时参数/配置选择错误;业务使用完毕无后续使用需求`（6 条）、`业务使用完毕无后续使用需求;其他;购买时参数/配置选择错误`（6 条）等——这些串里**同时含真负面片和占位片**，整串判负结论碰巧没错，但**摘要展示**时把占位词也带出来了（见根因 2 的展示问题）。

**根因 2（展示层）：feedbackReasonSummary 把占位词原样汇总进"负面反馈"文案。**
`buildRecommendedReason`（callbackRecommendations.js 第 209-231 行）与 `feedbackReasonSummary` 用 `summarizeRepeatedValues(orderedRecords.flatMap(getFeedbackReasonValues))`——**收集的是全部反馈值（含占位词）**，不是只收集判负命中的文本。于是"无/不涉及（14）"这类占位词被写进"反馈原因含负面表述（…）"的括号里，用户看到**"负面反馈"标签下写着"无/不涉及"**——即使用户 A 的负面判定实际由"任务操作流程不够简单快捷"命中，展示仍误导。实测：27 条 isNegativeFeedback=true 的建议里，27 条的 feedbackReasonSummary 都含占位词字样。
- **次级展示问题**：`recordHasNegativeFeedback` 走 `.some()` 只要有任一值判负即 true，而摘要把全部值并列——用户无法区分"哪个文本触发了负面判定"。

**修复方案（数据层 + 展示层各一处）：**

1. **数据层（判定修复）**：`recordHasNegativeFeedback` 改为先拆片再判：

```js

  return getFeedbackReasonValues(record).some((text) =>
    splitFeedbackReasonPieces(text).some((piece) => isSubstantiveFeedbackReason(piece)))
}
```
   - 效果：`其他;业务使用完毕无后续使用需求` 拆片后全为占位词 → 不判负（库内实测纠正 10 条纯占位拼接串）；`购买时参数/配置选择错误;业务使用完毕无后续使用需求` 拆片后首片仍判负 → 仍判负（正确，不误伤）。

   - **影响面确认**：`recordHasNegativeFeedback` 消费方 = libraryFilters（重点关注筛选）+ callbackRecommendations（负面触发路径）+ storyModel.test——语义都是"该记录是否含负面"，拆片版是**更严格的语义修正**，符合所有消费方预期。`scanTargets.js`（观察模块）已用 `splitFeedbackReasonPieces` + 逐片判定的正确姿势，可佐证本修复是"对齐既有正确先例"。

2. **展示层（摘要修复）**：`feedbackReasonSummary`/`buildRecommendedReason` 只汇总**判负命中**的文本：

- 新 repository（仿 postUseJiraRepository 的 decision 部分，独立文件 `server/postUseVisitDispatchRepository.js` 或并入现有文件均可——**建议独立文件**，保持与归档仓库对称）：
  - `list()` → 全量标记（payload JSON 解析，normalize）；
  - `markMany(items)` → `INSERT OR IGNORE`（**不可逆语义在 SQL 层兜底**：已标记的重复导出不报错、不覆盖首次时间）；bumpDataRevision()。
- 新路由（挂 postUseJira.js 同文件追加，权限与 decisions 一致：标记写操作用 `editRecord`，读用 `view`）：
  - `GET /api/post-use-visit-dispatch` → `{ items }`
  - `POST /api/post-use-visit-dispatch` → body `{ items: [{ itemKey, sourceType, dispatchedVia }] }`，审计日志 `post_use_visit_dispatch.mark`。

**2. 前端（PostUseCallbackProcessModal.jsx）**：
- 弹窗打开时（与 listPostUseCallbackDecisions 并列）拉 `listPostUseVisitDispatch()` → `dispatchedKeys: Set<itemKey>` + `dispatchedInfo: Map<itemKey, {dispatchedAt, dispatchedVia}>`。
- **"客服部回访"列渲染**（mergedFlagColumn 的 needCustomerVisit 变体，Bug1/2 修复后的 row 自带分组版）：
  - 组内任一 key 在 dispatchedKeys → 显示 `<Tag color="blue">已纳入</Tag>`（部分纳入时显示"已纳入（部分）"），无勾选框；
  - 未标记 → 正常勾选框（勾选态仍由 decisions 控制，跨会话持久——**与已纳入互不干扰**）。
- **标记时机**：
  - 「导出待客服部回访表」：`downloadFollowupTableExcel` 成功后（rows 非空）追加 `markVisitDispatched(rows, 'export')`；下载是本地动作无失败态，文件生成即标记。
  - 「发送待客服部回访」：SendMailModal `handleOk` 里 `sendMail` 成功后标记——**难点**：SendMailModal 是通用组件（无 onSent 回调），`buildAttachment` 是附件构建入口。**方案**：给 SendMailModal 加可选 `onSent` 回调 prop（发送成功 message.success 后调用），弹窗侧传入 rows 闭包标记 `'mail'`。改动小、语义清晰，通用组件向后兼容（其它调用方不传即无行为变化）。
  - **⚠️ 批判性审查修正（23:00）**：onSent 调用必须在 SendMailModal.handleOk 的成功分支内**自行 try/catch 吞错**、绝不 throw——否则标记 API 失败会穿透外层 catch，把 `message.success('已发送')` 错误地覆写成"发送失败"。吞错后另开 toast warning 提示"标记已纳入失败，可重新导出补标"。标记 API 失败不阻断主流程（清单仍可继续）。
- **存档按钮/发送按钮的 rows 收集**：已纳入的 itemKey 不再重复收集（`rows.filter((row) => !dispatchedKeys.has(row.itemKey))`）——与产品部回溯的 archivedKeys 过滤对称。**注意**：已纳入条目的客服部回访勾选态仍在 decisions 表保留（不可逆标记 ≠ 清勾选），只是不再进入导出/发送范围。
- **底部统计**："已勾选客服部回访 N 条"文案追加"· 已纳入 M 条"（M = currentKeys 中 dispatchedKeys 命中数），让用户感知交接进度。
