## 2. 设计总则

1. **与工单侧同构**：同一张脸（face 卡片）、同一套锚点与前后对比口径（`resolveActionAnchor` +
   `computeReduction` 原样复用，scheduleAt-only 口径 11-25 拍板不动）。
2. **月份 = 趋势轴，不进签名**。用户原始提议"产品×来源×月份"——若月份进签名，同一问题被切成
   单月碎片（每面恒 1 条），趋势图退化成孤点、前后对比永远"数据不足"，压降语义直接失效。
   工单侧正是把月份留给趋势轴才有了效果验证。月份信息不丢：face 显示**首末月区间**
   （firstMonth–lastMonth），趋势图 X 轴即月份。
3. **来源进签名，粒度两级**：签名 = `productName | sourceKind`，sourceKind ∈ {trace, visit}
   （产品部溯源 / 省代表回访）。溯源内部的细分（问卷类 questionnaire / 投诉回访 callback_non_ten）
   作**辅助 Tag** 展示，不进签名——与工单侧"问题类型/请求场景进展示不进签名"同构。
4. **样本判据同源**：face 的反馈样例取组内**最长文本**（信息量最大）——与回访预导入
   （同身份取信息量最大反馈）、11-27 迁移脚本同一判据，不新造规则。

## 3. 聚合模型（新领域函数）

新文件 `src/domain/postUseActionProblemScope.js`（不塞进 actionProblemScope.js，那文件的
签名语义是工单专属；复用其两个纯函数 import）：

```
buildPostUseActionProblemScope(action, { traces, visits })
  → { problems: PostUseProblemFace[], anchorDate, anchorMonth }
```

- 签名键：`${productName} | ${sourceKind}`；组内记录 = 该举措关联的 traces（sourceKind='trace'）
  / visits（sourceKind='visit'）。
- 每 face 字段（对齐工单 face 结构 + post_use 特化）：
  - `productName` / `sourceKindLabel`（产品部溯源｜省代表回访）
  - `recordCount`（N 条，非"N 单"——溯源/回访不是工单）
  - `subTypeLabel`：trace 的 sourceType plurality（问卷类｜投诉回访）；visit 为空
  - `statusLabel`：trace 状态 plurality（待处理/处理中/已处理）；visit 用共享谓词
    `visitEvaluationState` plurality（已评估/评估中/待评估）
  - `feedbackSample`：组内最长 customerFeedback（trace）/ userFeedbackText（visit）
  - `firstMonth / lastMonth`：月份区间（排序后首末）
  - `monthlyTrend`：`{ date, count }[]`——**月份解析特化**（见 §4）
  - `reduction`：`computeReduction(trend, anchorMonth)` 原样复用
- 无关联记录 → `{ problems: [] }`（UI 走降级，不造快照 face——工单侧的快照兜底 face 在
  分区3 被 `ticketCount>0` 过滤本就不显示，post_use 侧保持同样的"无关联即不出面"行为）。

## 4. 月份解析特化（与工单侧的关键差异）

工单记录 `importMonth` 恒单月；**溯源记录的 `importMonth` 可能是"、"分隔多月份文本**
（清单 tab 的跨月行，如 `2026-09、2026-10`——postUseJiraRepository.list 的既有注释）。
直接喂 `monthlyTrend` 会产出 `"2026-09、2026-10"` 这种假月份键。

规则：`splitImportMonths(trace)` 按"、"拆分去空；一条多月份溯源记录在其覆盖的**每个月各计 1 条**
（与清单 tab"一行覆盖多月"的语义一致）。visit 取 `importMonth || visitMonth`（单月）；
两者皆空的记录仍计入 face 的 recordCount，但不进趋势。

## 5. UI 落点（两处，均在 ActionItemDrawer）

### 分区3 关联问题（新组件 `PostUseProblemFaces.jsx`）

  ? <PostUseProblemFaces problems={postUseScope.problems} />

face 卡片形态（抄工单 face 的 sub-section-box 结构）：

→ 次行小字 `2026-09 ~ 2026-11`（月份区间，空则省略）。
「问题（举措快照）」块位置不动（快照=创建时定格文本，与聚合面互补不互斥）。

### 分区5 效果验证（改造 `ActionProblemScopePanel`）

面板改**接收预构建 scope**（调用方 = 分区5 唯一消费点，契约变更安全）：

```
<ActionProblemScopePanel
  scope={item.source === 'post_use' ? postUseScope : ticketScope}
  unitLabel={item.source === 'post_use' ? '条' : '单'}
  areaName={item.source === 'post_use' ? '反馈条数' : '工单数'}
  emptyText={item.source === 'post_use' ? '暂无关联溯源/回访，无法做效果验证' : 原文案}
/>
```

- post_use 趋势图只画一条线（count；溯源/回访无"负向情绪"维度，不画第二条）。
- 参考线/锚点行、ReductionDetail、'关联趋势，非因果' 免责声明原样保留（人手工关联的记录，
  趋势反映的是关联证据的月度分布——与工单侧同caveat，如实声明）。
- ReductionDetail 文案的"单"按 unitLabel 参数化。

### 数据流

`postUseSources` 已在抽屉 fetch（useEffect, source==='post_use' 时）——分区3/4/5 共用同一份，
**不新增请求**。postUseScope = `useMemo(buildPostUseActionProblemScope(item, postUseSources), …)`。

## 6. 边界与降级

| 场景 | 行为 |
|---|---|
| 无任何关联溯源/回访 | 分区3 走原降级 Tag 行；分区5 Empty（post_use 文案） |
| 关联记录全部无月份 | face 正常出（recordCount/样例/状态），趋势为空 → reduction=null → "未设排期/无趋势"如实 |
| 关联记录全部无反馈文本 | face 出，样例行省略；不造占位文案 |
| 多月份溯源字符串 | §4 拆分计月 |
| 措施已有 painPointSnapshot | 分区3"问题（举措快照）"照常显示，与聚合面并存 |

## 9. 拍板结论（2026-11-27，详见文档头）

1. **来源粒度 = 两类**：溯源 / 回访各自成面；溯源细分（问卷类/投诉回访）进辅助 Tag。
2. **压降口径 = linked-only**：趋势 = 该举措自己关联的记录月度分布，与工单抽屉侧同构。
3. **回访面评估状态 Tag = 默认展示**（visitEvaluationState plurality）。
4. **图上举措时间线**：锚点口径与问题压降 tab 完全同源（resolveActionAnchor，
   scheduleAt-only，无排期不画线）；形态为抽屉式单条参考线 + ReductionDetail 前后对比
   （同月多举措月聚合角标是 tab 多举措叠加专属，不进抽屉）。
