# 设计 · 首页「行动建议」呈现方案

> 目标：在洞察工作台**概览首页**上，把"要关注的问题"以分类分层的方式呈现，支持规模/建议/纳入优化状态一目了然，并可下钻到抽屉看关联举措与工单，可导出 MD 报告。
> 状态：设计方案（待评审，未实现）。

## 0. 与既有设计决策的关系（先对齐，避免反复）

- 之前"**保持融入到整体结构中**"这条约束，是针对**工单 tab（投诉/咨询）**——不要在工单 tab 上另挂螺栓式"行动建议"面板。本方案是**概览首页**模块，首页本来就承载"要关注什么"的归纳视图（现有 `PlanningRecommendationsPanel` 即在此），故不冲突。
- 首页模块用**信号驱动分层**（来自已验证的 EIP 原型与 `CALIBRATION-阈值-EIP.md`），而不是固定三块模板，保证每月报告因"异动 + 小而锐"而不同。
- "纳入优化状态"**不新造模型**：代码已有 `requirementTicketProgress` 领域 + `ActionItem.sourceRecommendationId === rec.id` 桥，直接复用（详见 §5）。

## 1. 信息架构：分类 + 分层

**分层（顶层，按"需要被关注的紧迫性/性质"）** = 5 段信号驱动。下面逐层给出**分类依据**与**价值**，避免"模板化"——每层的存在都对应一个明确的决策动作。

| 层 | 分类依据（进入条件） | 价值（它驱动什么决策） |
|---|---|---|
| **长期结构性** | 跨期持续（≥2 分析周期）且 单量 ≥ S(结构性门槛，按产品相对化) | **防止"习以为常"**：量大且持续 = 必须有常设责任归属，不能靠临时工单应付。优先级最高的"站着也要解决"类。诚实标注"每月都出现，正因为一直没解决"——把"雷同"翻成"该排期的证据"。 |
| **本月异动** | 跨期环比满足双判据 `|环比%|≥50% 且 |Δ绝对|≥Δ阈值(随产品体量缩放)`；**横切信号**，可与结构性/小而锐共存 | **让每月报告不同**：抓新火、验证旧改是否真闭环（骤降项需确认非自然消退）。是报告差异性的唯一来源。骤降项标注"需确认是否真闭环"。 |
| **小而锐** | 投诉率 ≥ H(高害门槛=max(0.15, 3×产品投诉基线)) 且未达结构性体量 | **防止"长尾埋高害"**：量可小但"踩到的人几乎都投诉"，是体验雷区，必须单列挖出。用户最在意的"被掩盖问题"主力来源。 |
| **常规迭代池** | L(长尾门槛) ≤ 单量 < S 且 投诉率 < H | **给中等量低害问题归宿**：并入产品常规体验迭代**顺手做掉**，不单独开项目、不挤占优先级。可批处理的工作项池。 |
| **长尾** | 单量 < L 且 投诉率 < H | **显式声明"暂不动作、仅监控"**：透明、避免 clutter、避免对小样本过度反应（抽样噪声）。"知道它在、但不值得现在投入"的清单。 |

**保留 5 层、不合并"常规迭代池+长尾"的理由**：两者虽都低害，但决策含义相反——前者"值得排一次迭代"，后者"暂不动"。合并会 reintroduce 用户曾批评的"把问题埋进笼统长尾"风险。分界见 §1.1。

**分类（每层内的卡片）** = 派生主题（L1 家族 → L2 子议题），按已验证的正则分类法（原因优先、痛点兜底）聚类。

> 每个问题 = 一张卡片。高害小项（小而锐）绝不埋进长尾；常规迭代池单列不塞长尾。

### 1.1 常规迭代池 vs 长尾 的分界线（明确）

两者都低害（投诉率 < H），唯一区分是**体量**：

- **长尾门槛 L** = `max(3, round(0.01 × T))`，封顶 10。
  - 单量 < L 且低害 → **长尾**（监控即可）
  - L ≤ 单量 < S 且低害 → **常规迭代池**（排入常规迭代）
- 直觉：L 是"是否值得为它专门排一次迭代"的**最小工单量**。低于它=长尾；达到它=进迭代池。
- 量级参考（EIP L=10）：产品规格(5单)<10→长尾；带宽升降配(53单)≥10→常规迭代池。与 `CALIBRATION-阈值-EIP.md` 一致。

### 1.2 进入条件按产品分别设置（相对化阈值）

四产品总量差 **32×**（EIP 2393 vs ELB 75），且**投诉基线差 7×**（EIP 5.6% vs VPC 40.2%）。若用全局固定阈值：
- 全局"高害 17%"对 VPC(基线40%) 形同虚设 → 永远捞不出"小而锐"；
- 全局"Δ绝对≥10单"对 ELB(总量75) 相当于整产品的 13% → 误判一切为异动。

故所有门槛**按产品相对化**，公式与实测值如下（T=产品区间工单总量，B=产品投诉基线=投诉工单数/T）：

```
H(高害门槛) = max(0.15, 3 × B)          // 小而锐
S(结构性门槛) = max(10, round(0.10 × T)) // 长期结构性
L(长尾门槛) = max(3, round(0.01 × T)) 封顶 10   // 常规迭代池 vs 长尾
Δ(异动绝对阈值) = clamp(round(0.01 × T), 3, 12) // 本月异动双判据
```

| 产品 | T | B(投诉基线) | H(高害≥) | S(结构性≥) | L(长尾<) | 异动Δ≥ |
|---|---|---|---|---|---|---|
| 弹性公网IP | 2393 | 5.6% | **17%** | 239 | 10 | 12 |
| 云专线 | 113 | 26.5% | **80%** | 11 | 3 | 3 |
| 虚拟私有云 | 122 | 40.2% | **100%** | 12 | 3 | 3 |
| 弹性负载均衡 | 75 | 22.7% | **68%** | 10 | 3 | 3 |

> 注：小型产品(云专线/VPC/ELB) 最大单问题仅 1–3 单，故届时**可能无"长期结构性"问题**——属正常（量太小、无主导 recurring 主题），由 常规迭代池+小而锐 承载。具体数值待分类法在其余 3 产品跑通后，用真实子议题分布做最终校准（公式不变，仅微调系数）。EIP 的 H=17%/L=10/Δ=10 已在 `CALIBRATION-阈值-EIP.md` 校准，与公式给出的 17%/10/12 同量级。

## 2. 卡片要素（你要求的"三类信息"）

每张卡片固定三要素 + 标题：

1. **标题**：`L1家族 · L2子议题`（如 `网络质量 · 丢包`）
2. **规模情况**（一行星级徽章）：
   - 工单量 `N 单`
   - 环比 `±X%`（异动层强制显示 Δ绝对）
   - 投诉率 `Y%`（来自 `_src` 逐单口径），**其后紧跟 `投诉 a / 咨询 b`**（该问题内逐单 `_src` 拆分出的投诉工单数 a、咨询工单数 b，a+b=N）
   - 加急率 `Z%`
3. **建议**（一条清晰动作，不堆候选动作）：如"端到端丢包诊断工具"
4. **是否纳入优化**（状态徽章，见 §5）：
   - `已纳入 · 进行中` / `已纳入 · 已完成` → 绿色
   - `未纳入 · 盲区` → 红色（催拍板；这正是"数据在尖叫但没人管"的点）

## 3. 详情抽屉（点击卡片打开，右侧滑入）

抽屉内分区，对应你要的"具体关联的举措"和"这类问题涉及的工单"：

### 3.1 关联举措
- **确立举措（层B，权威）**：来自 `ActionItem`（经需求工单关联解析出的 `derivedStatus`）。显示举措名 + 需求工单号 + 计划完成时间。
- **候选动作（层A，LLM 聚合）**：3–8 条带频次的候选动作（如"端到端丢包检测(18) / 丢包自动定位(12) / 诊断报告导出(7)"），作补充参考。
- 若两层皆空 → 显示"暂无确立举措，建议本月排期"，并挂盲区标记。

### 3.2 涉及工单（支持按 投诉/咨询 筛选）
- 表格：工单号 | 类型(投诉/咨询，逐单 `_src`) | 月份 | 是否加急 | 客户请求内容摘要。
- **筛选器**：按 `_src` 提供「全部 / 仅投诉 / 仅咨询」切换（加急筛选暂不做，后续可加）。筛选仅影响本表格显示，不改变卡片上的汇总数字。
- 行可展开看完整工单（真声 + 痛点摘要 + 复核根因）。
- 数据来自 `rec.evidenceTicketIds` → 经工单存储按 id 解析（需确认首页已有 feedbacks/工单查询入口）。

### 3.3 真声 + 摘要（双层，沿用备忘录约定）
- 真声（`客户请求内容`/`受理内容`/`处理意见`）+ 〔痛点摘要〕`需求痛点` + 〔复核根因〕`问题原因`，严格按字段出处标注，杜绝把分析层当原话。

## 5. 数据契约与桥接（关键：复用现有模型）

### 5.1 扩展 `OverviewRecommendation`（现有契约见 `src/domain/overviewConclusions.js`）
新增字段（不破坏旧字段）：
```
tier: 'structural' | 'change' | 'sharp' | 'iteration' | 'tail'
scale: { ticketCount, moMPct, moMAbs, complaintRate, urgentRate }
recommendation: string            // 一条清晰建议
customerVoice: { verbatim, summaryLabel:'痛点摘要'|'复核根因', summaryText }
actionsLayerA: { text, freq }[]   // 候选动作（层A 聚合）
evidenceTicketIds: string[]       // 已有，抽屉用
stableKey: string                 // 已有，跨月稳定主键
sourceRecommendationId: string    // 与 ActionItem 桥接（见下）
```

### 5.2 "是否纳入优化"如何算（零新模型，分两档呈现）
- 桥：`ActionItem.sourceRecommendationId === rec.id`（`src/components/topicAnalysis/*`、`PlanningRecommendationsPanel` 已用此桥）。
- 解析：`enrichActionItemWithRequirementProgress(item, progressById, mappingByWorkflowStatus)`（`src/domain/requirementTicketProgress.js`）→ 取 `derivedStatus`。
- 判定（**区分两档**，不合并）：
  - `derivedStatus === 'in_progress'` → **已纳入 · 进行中**（黄/蓝徽章）
  - `derivedStatus === 'completed'` → **已纳入 · 已完成**（绿徽章）
  - 无关联 ActionItem 或 `derivedStatus` 为空/其他 → **未纳入 · 盲区**（红徽章，催拍板）
- 该领域已支持"需求工单 → 操作状态(开发中/联调中→in_progress、已完成→completed) → 聚合状态"，直接复用即可。两档分别呈现，便于区分"已落地"与"在做"。

### 5.3 工单详情解析
- 抽屉"涉及工单"需按 `evidenceTicketIds` 取完整工单。需确认首页是否已有工单查询入口（推测来自 `snapshot` 或 feedbacks store）；若无，新增一个 `getTicketsByIds(ids)` 解析器（复用现有 feedbacks 数据）。
