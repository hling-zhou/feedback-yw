# DESIGN — 用后即评抽屉优化建议（自动生成）· 省代表回访 + 产品部回溯

> 涉及：PostUseVisitDrawer（省代表回访）、PostUseJiraDrawer（产品部回溯/溯源）。
> 机制复用投诉/咨询工单既有优化建议链路（ticketOptimizationExtract / ticketOptimizationLLM / 来源 Tag / 后台任务框架）。
> 本文档为终版方案，含 2026-11-19 全部用户拍板；落地与验收以本文档为基准。
> 复核真源 = 代码（postUseOptimization.js / PostUseOptimizationSection.jsx / enrichRunner.js / customerVisitImport.js / postUseJiraExport.js 等）。

---

## 1. 需求与拍板记录（决策日志）

| # | 事项 | 拍板（2026-11-19） |
|---|------|------|
| 1 | 生成时机 | **「批量手动 + 抽屉单条」两入口**（对齐补全用户旅程先例）；不做导入后自动跑 |
| 2 | 内部评估是否进语料 | **不进**（优化建议基于客户声音，内部判断可能反向污染） |
| 3 | 投诉回访类溯源语料 | **拼原投诉工单处理意见**（跨表增强：scoreSource=投诉回访 且有 originalTicketId 时，从 records 表按工单号取处理意见追加） |
| 4 | prompt 措辞 | **零漂移复用工单 prompt + 调用方语料层加场景前缀**（如 `[省代表回访反馈]`），共享 prompt 单源一个字不改；模型心智靠前缀对齐，工单侧未来修 prompt 回访侧自动跟进 |
| 5 | 导出/导入 | **导出加**：两视图导出表末尾追加「产品/技术优化（自动）」「服务/流程改进（自动）」两列；**导入不加**：导入表若带这两列，现有解析天然跳过（按必需表头映射取值，额外列不进映射），补守卫测试锁定 |

## 2. 语料口径（单源函数，落地前先 dump 真实 payload 抽样核对）

| 宿主 | 语料拼接顺序（先取到先停，换行拼接） | 依据 |
|------|------|------|
| 省代表回访 visit | ① 客户反馈 `userFeedbackText` ② 回访结果 `visitFeedbackDetail → visitResult` 兜底 | 拍板 6 |
| 产品部溯源 trace | ① 客户反馈 `customerFeedback` ② `scoreSource=投诉回访 && originalTicketId` 时追加【原投诉工单处理意见】段（records 表 complaint_ticket 按 ticketId 取，处理意见截取口径 = `split('处理意见：')[-1]`，与打标复核基准一致） | 拍板 3+6 |

- 内部评估/内部结论/回溯结果/备注 **不进语料**（拍板 2）。
- 场景前缀（拍板 4）：visit = `[省代表回访反馈]`；trace = `[产品部溯源·客户反馈]`。
- 跨表查不到原工单（未入库/已删）→ 静默只用品类反馈语料，不报错不阻断。
- 字段读取**不套 product/product 双读**（visit/trace 是独立领域实体，字段真源各自为 `productName`，11-18 拍板口径）。

## 3. 数据模型（零迁移）

复用 record 层字段名，不发明新同义字段：

```
optimizationProduct  string   产品/技术优化（≤3 条，换行分隔）
optimizationService  string   服务/流程改进（≤2 条，换行分隔；可为空）
optimizationSource   string   'rule' | 'llm'（如实标注：LLM 失败回退规则结果必须标 'rule'）
```

- 省代表回访：内嵌 `meta.post_use_visit_records_v1` 各 record（meta 无 schema，天然兼容）。
- 产品部溯源：内嵌 `post_use_jira_items.payload`（`normalizeJiraItem` 归一化补三个 String 字段）。

## 4. 生成链路（新增薄适配层，单源）

新增 `src/lib/postUseRating/postUseOptimization.js`：

1. `collectPostUseOptimizationText(entity, entityType)` — 语料单源（§2 口径）；
2. `needsPostUseOptimization(entity)` — 有语料且 `optimizationProduct` 为空 → 待生成（批量过滤与计数同源）；
3. `generatePostUseOptimizations(entity, entityType, settings, extras)` —
   - LLM 优先：调 `extractTicketOptimizationsWithLLM`（**prompt 零改动复用**），extras 传产品名与 KB snippets；
   - KB 检索：按 `productName` → 目录 key 解析（消费前 `loadManagedProductCatalog` 刷新，catalogCacheCoverageGuard 口径），`buildKnowledgeQuery` 需要 record 形态 → 构造最小 record { productKey, rawText: 语料 } 传入；
   - LLM 失败/未配置 → 回退 `extractTicketOptimizations`（规则兜底，纯函数直接调用）；
   - 来源如实标注：LLM 真实产出标 'llm'；回退标 'rule'；
4. `applyPostUseOptimizationPatch(entity, result)` — 浅拷贝合并三字段。

## 5. 触发入口

| 入口 | 形态 | 说明 |
|---|---|---|
| 批量生成 | 两 tab 工具条「生成优化建议」按钮 + 待生成计数 | `runEnrichment` 新增 `mode='post_use_optimization'`、`taskType='retag'`（复用任务面板与互斥体系，前端任务列表零改动）；参数 `entityType('visit'\|'trace')` + 月份范围；批次节奏对齐 FLUSH_BATCH_SIZE=4；计数接口对齐 post-use-journey/pending-count 先例 |
| 单条生成 | 抽屉模块右上「生成」按钮（retag 权限；无内容时显示） | 同步接口 `POST /api/post-use-optimization {entityType, id}`；批量任务进行中 → 409 |

**写回防覆盖（拍板 7）**：批量/单条写回一律 **re-read 最新库值 → 只 merge 优化三字段 → 落盘**，禁止整条覆盖；记录已删则跳过。visit 走 getMeta → 按 id 定位 → merge → putMeta；trace 走 repository 新增 merge 方法（payload merge，不触碰 status/assignee 等其他字段）。

## 6. UI（共享组件，同源判定纪律）

新建 `src/components/feedbacks/PostUseOptimizationSection.jsx`，两抽屉引用同一实现：

- 位置：基础信息 Descriptions 之后、经办人/评估表单之前；
- 模块标题「优化建议（自动生成）」用宿主同款 `Typography.Text type="secondary"`（对齐「基础信息」标题写法）；
- 行结构与文案对齐工单抽屉：`产品/技术优化（自动）` 恒显（空显 '—'）；`服务/流程改进（自动）` 有值才显；bordered `Descriptions`（跟随两宿主现状，不搬 FeedbackDrawer 新版堆叠式）；
- 来源 Tag 复用 `AutoOptimizationSourceTag`，**空内容时不显示**（没生成过标"规则"= 来源失真）；
- 空态：两行 '—' + 底部一行 12px 说明「未生成，可通过列表页或右上按钮生成」。

## 7. 导出/导入（拍板 5）

- **导出加列**：`buildPostUseJiraExportRows` 末尾追加 `产品/技术优化（自动）` `服务/流程改进（自动）`；`buildPostUseCustomerVisitRows` 同款追加到 21 列模板段之后的推荐分析段末尾；
- **导入跳过**：jira 导入 `HEADER_FIELDS` 按必需表头映射取值，额外列天然不进映射——守卫测试锁定（导入表带此两列：不报错、不回写、不影响行校验）；visit 导入 columnMap 同理（列映射制，未知列天然忽略）；
- **显式声明语义边界**：跳过 = 导出表上的建议文本**不通过回导写回库**；库内建议只能由生成链路更新。导出表手工改建议再回导 = 改动静默丢失（"导入不加"的自然结果，已在本文档声明，防后续排障误会）。

## 8. 覆盖风险与联动（防缺陷触发规则对照）

| 风险 | 对策 |
|---|---|
| 回访重导静默清掉优化建议（customerVisitImport 覆盖合并按模板列重建对象，只保 4 个受保护域） | **必须在合并处显式保留三字段**（对齐 actionIds 保留先例）；守卫用例红绿证明 |
| 批量写回覆盖在线编辑（评估/经办人/回溯结果） | re-read → 只 merge 三字段 → 落盘（§5）；merge 用例：批量期间人工先改评估 → 写回后评估保留 |
| 删除联动 | 字段内嵌 payload 随记录删除，无独立存储需清理，天然安全 |
| jira importMany/archiveMany 白名单 fields 更新 | 白名单不扩即天然保留三字段，守卫用例确认 |
| 服务端目录缓存陈旧 | 消费 getCatalogProducts() 前 loadManagedProductCatalog（catalogCacheCoverageGuard 口径） |
| 批量 vs 单条并发 | 单条接口查任务锁，批量进行中 409 |
| 来源标注失真 | LLM 失败回退必须标 'rule'（来源标注纪律）；已有值不重生成（幂等：needsPostUseOptimization 判空） |

## 9. 实施计划与测试

**排期**：服务端链路（含重导保留 + 导出列）→ enrichRunner 新 mode + 单条接口 → UI 共享组件接入两抽屉 → 测试守卫与真机确认。

**测试清单**：
1. 纯函数单测：语料拼接（visit/trace 两口径 + 投诉回访跨表段）/ needs 判定 / LLM 失败回退标 'rule' / 场景前缀；
2. 重导保留守卫（红绿证明：注释保留逻辑应红）；
3. 批量写回 merge 用例（在线编辑不被覆盖）；
4. 导入跳过守卫（jira 导入表带两列：不报错不回写）；
5. 导出列用例（两视图行构建含新列且在末位）；
6. 渲染测试：两抽屉 renderToStaticMarkup 空态 + 有值态；
7. 真实链路验证：node -e 用真实 visit/trace payload 形态跑 collect → generate(mock) → apply → 写盘 → 重读全链（禁 fixture 反推）；
8. typecheck 触碰文件 TS 零新增；UI 结构改动需真机目检并在交付说明显式声明"已/未真机确认"。

**验收口径**：
1. 两抽屉基础信息下方可见「优化建议（自动生成）」模块，行文案与工单抽屉一致；
2. 批量入口跑完后计数清零、来源 Tag 如实（大模型/规则）；
3. 重导后已有建议仍在；批量期间在线编辑不丢；
4. 导出表末尾两列有值；带两列的导出表直接回导不报错、库内建议不被覆盖。
