# 防缺陷触发规则（开发约定）

> 来源：2026-11-06 建议回访/溯源清单五问题复盘 + 同日「待补全旅程」深度复盘补充规则 6/7。规则挂在**具体动作**上——做到对应动作时必须回答对应问题，不依赖"记得"。
> 适用：本仓库所有协作者（含 AI 辅助开发）。

## 五条触发规则

### 1. 写任何 DELETE 路由 / 删除实体 → 必答"还有谁持有这个键"

删除操作影响的不只是被删实体——所有引用它的表和状态（勾选/标记/缓存/角标）都要过一遍：

- 哪些表/前端状态持有它的键？（grep itemKey / 外键字段）
- 悬空后会表现成什么 bug？
- 谁负责联动清理？——**在仓库层/服务端做**（覆盖单删/批删/未来 API 全部入口），不放某个前端页面（漏入口）。

先例：删除产品部回溯归档条目未联动取消 decisions 勾选 → `postUseJiraRepository.clearTraceDecisionsForDeletedItem`。

### 2. 写任何计数 / 角标 / 待办数 → 必写"何时归零"

提醒类数字必须先定义归零条件（通常 = 排除已完结条目），再写谓词：

- "已纳入/已处理/已完结的要不要排除？"——**默认排除**。
- 完结态实体常因"勾选保留、经办人另存"类设计把提醒计数永久占住。

先例：角标（待指定经办人数）把已归档行永久计入，存档提示误报。

### 3. 同一业务判定第 3 处出现 → 强制抽共享谓词

同一概念（已纳入 / 勾选 / 已归档…）多处各写一份内联过滤 = 判定漂移 = 必然出现"Tag 显示 12 条、筛选结果 0 条""行显示勾选、按钮说没勾"类矛盾：

- 新增任何呈现（Tag/筛选/计数/角标/按钮态）前先问：**这个概念已有哪些判定点？**
- 全部走同一判定函数或同一段派生数据；粒度差异（行级/组级）显式命名，不内联重写。

**已固化工具**：`node scripts/audit-shared-predicates.mjs`——扫描 src/ 直摸底层数据结构绕过共享谓词（isArchived / isDispatched / decisionOf）的代码，有绕过 exit 1，可接 CI。新抽共享谓词后在脚本 `SHARED_PREDICATES` 登记表中追加概念即可。

### 4. 方案级改动 → 必有"链路外的真实证据"

方案级（键结构 / 存储结构 / 口径 / 跨模块）改动，**测试全绿不算完成**——单测 fixture 常与真实链路形态不符（同一场事故：fixture 数组形态、链路 Set 形态，测试与实现共享同一错误假设，红绿证明对现实失效）：

- 至少一段真实证据：真实入参跑通完整调用链（node -e / 最小脚本）/ 生产形态数据 dump 对照 / 真机操作一次。
- 守卫测试锚定在**链路层**（走完整构建函数），不锚在纯函数层（纯函数守卫抓不到链路形态断裂）。

先例：`storyModel.test.js` 的"方案B 崩溃回归"用例——走完整 `buildPostUseStoryModel` 断言行键带月份段。

### 5. 给状态/动作定存储键（身份）→ 先答"它针对什么而存在"

动作类对象的身份 = **客体 + 时间界**。键缺时间界 = 把一次性事件建模成永久属性：

- "纳入回溯"针对的是"客户×产品×某月的发现"（一次性），不是"客户×产品"（永久实体）——键里缺月份导致跨月串扰。
- 拍板粒度类设计时，把隐含业务假设写成一句话请业务方确认（"处理一次是永久处理，还是按月独立？"）——假设没确认不算设计完成。
- 设计级修复（改键粒度/存储/口径）不能按普通 bug 修：全消费方清单 → 逐个验证 → 迁移方案 → 真实链路验证，风险高于修 bug。

### 6. 改共享解析层/共享工具函数 → 必答"谁在依赖这个返回形态"

共享层的返回形态就是契约。82742ef 教训：为 assistant 粘连场景给 `pickAssistantPayload` 加"取最后一个完整对象"启发式，静默剥掉了打标类消费方的 `{"results":[...]}` 批容器包装 → 6+ 个消费方批量模型答案整体丢失、回退本地还被误标 `journeySource:'llm'` → 红测试亮了 28 天无人问。

- 改共享函数返回形态前，grep 全部消费方，逐一回答"它期望什么形态"。
- 共享解析层的消费方场景不同（assistant 单对象 vs 打标批容器）→ 形态判定必须显式分支，不能一个启发式通吃。
- 改完必跑共享层的契约守卫测试（先例：llmClient.test.js 批容器契约 5 用例）；红着的历史测试不是"已知失败"，是**在报生产断裂**——先弄清它为什么红再决定动不动它。

### 7. 写"来源标注"字段（journeySource/source 类）→ 标注必须与事实同源

来源标注是下游口径的输入，失真标注 = 污染下游一切判定：

- 写标注时必答：这个值真的是这个来源产出的吗？回退/兜底路径产出的值必须标真实来源，不得沿用"主路径"的标注。
- 先例：模型答案未送达时 578 段用 UNKNOWN 占位 + 本地重匹配，362 行仍无条件标 'llm' → 下游 classifyPostUseJourney 把本地结果当"模型已判"→ 默认永不重试 → 待补计数静默漂移（修复 = llmVerdict 区分「模型真实判断」与「答案未送达回退」）。
- 消费口径字段前先问：**这个字段的生产方是否如实标注？** 数据真源失真时，下游一切口径修复都是沙上建塔。

## 排查约定

用户报"行为不对"时，先**分层归因**再定方案：同一现象可能来自"设计本来如此"（键粒度选择）也可能来自"实现没生效"（形态断裂）。**第一动作 = dump 实际数据形态**（存储的键/值长什么样），不要直接跳到设计层推方案。
另：**修口径类问题前先验证口径输入的真源**（如 journeySource 是否如实标注）——"分类没错但分到错误的类"和"分类对了但输入是假的"是两个完全不同的问题，修错方向会白走一轮。

## 维护

- 规则新增/修订：先在本文件登记，再考虑代码化（审计脚本/守卫测试）。
- 全部规则的跨项目版本沉淀于 AI 侧全局记忆（防缺陷纪律，2026-11-06），本文件是项目内的对等版本，供人工 review 与新成员阅读。
