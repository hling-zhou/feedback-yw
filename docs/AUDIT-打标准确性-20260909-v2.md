## 四、问题类型(problemType)——**P0 误标 115 条**

### 4.1 配额申请误标为"可用性/连通性故障"

| 指标 | 数量 |
|------|------|
| 标为"可用性/连通性故障"但客户请求+处理意见均为纯配额申请 | **115 条** |

**典型样本（处理意见全文确认为配额提升）**:

> 工单1: cr="申请华南-广州3资源池带宽配额提升至7644M"  
> 处理意见: "华南-广州3单资源池带宽配额已提升至7644M，有效期到8月13日，请您于有效期前订购。到期后恢复原配额值"  
> problemType: **可用性/连通性故障** ← 应为 配额与权限申请

> 工单2: cr="订购云主机时提示弹性公网IP全局配额超限，剩余可订购量为0，请协助扩容配额1个"  
> 处理意见: "请协助扩容配额1个" → 提交配额申请  
> problemType: **可用性/连通性故障** ← 应为 配额与权限申请

**根因**: 配额工单中含"可能导致业务中断"等措辞，触发了 `matchesAvailability` 的故障关键词匹配。此问题已在 `problemTypeClassifier.js` 中修复（加 `QUOTA_CONTEXT_RE` 排除），但 **修复前导入的 115 条工单需要 retag**。

### 4.2 安全组问题未标为配置类

初步检测 29 条，但深层抽查显示较多假阳性（如 SDK API 查询标注为"产品功能咨询"实为正确）。**此问题需人工逐条确认，不建议批量修改**。

### 5.3 匹配度问题（对照处理意见全文）

**大量优化建议与实际处理意见描述的问题不匹配**。典型不匹配模式：

> 工单: 弹性负载均衡安装交付 + 复现故障  
> 优化建议: "在绑定成功页增加高频业务端口连通性一键检测，自动识别安全组/ACL 拦截并提示一键放行"  
> **问题**: 工单是负载均衡问题，建议却是安全组检测——完全不对口

> 工单: EIP 带宽告警（云监控短信用量超阈值）  
> 优化建议: "在绑定成功页增加高频业务端口连通性一键检测，自动识别安全组/ACL 拦截并提示一键放行"  
> **问题**: 带宽用量告警与安全组无关

> 工单: "ECS之间100%丢包，请帮忙回溯流量分析"  
> 优化建议: "在绑定成功页增加高频业务端口连通性一键检测，自动识别安全组/ACL 拦截并提示一键放行"  
> **问题**: 100%丢包需要流量分析，不是安全组规则自检

**根因**: 优化建议按 journey 产品套模板派发（来自 `ticketOptimizationExtract.js` 的 `JOURNEY_PRODUCT_TIPS`），没有根据处理意见中的具体根因/结论做个性化调整。

## 六、总结与建议

### P0 - 必须处理
1. **requestScene 补标**: 2716 条工单 requestScene 为空（93%），需要全量重跑打标 pipeline。建议按 `run-loop.cjs` 流程，先过 `validate-action-recs.cjs --emit` 写入产物，再过 `gate-check.cjs` 验证。
2. **problemType 误标修复**: 115 条配额工单标为"可用性/连通性故障"，已在 `problemTypeClassifier.js` 修复代码，需在执行 retag 时一并纠正。

### P1 - 应处理
3. **优化建议模板化**: 当前 `ticketOptimizationExtract.js` 的 `JOURNEY_PRODUCT_TIPS` 按 journey 产品派发，建议增加基于处理意见根因/结论的个性化补充通道（利用 `handlingSignalExtract.js` 中已实现的结论方向识别能力）。

### P2 - 可延后
4. **customerRequest/painPoint 来源标记**: 93% 的 source="?" 不利于追溯。建议导入时写清 source="xlsx_import"，pipeline 重新提取后更新为 "rule"/"llm"。
5. **painPoint 增量**: 16 条与 cr 完全相同，后续若有 LLM 增强流程，可优先给这些工单做痛点补全。
