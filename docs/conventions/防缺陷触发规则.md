# 防缺陷触发规则（开发约定）

> 来源：2026-11-06 建议回访/溯源清单五问题复盘 + 同日「待补全旅程」深度复盘补充规则 6/7 + 2026-11-09 弹窗勾选态矛盾复盘扩展规则 1 + 2026-11-10 需求三段闭环测试复盘扩展规则 2（linkageError）/ 深夜部署数据修复复盘补充规则 8-11 + 2026-11-25 万投比 tab 丢失 72 天复盘补充规则 24/25。规则挂在**具体动作**上——做到对应动作时必须回答对应问题，不依赖"记得"。
> 适用：本仓库所有协作者（含 AI 辅助开发）。

## 触发规则

### 1. 写任何 DELETE 路由 / 删除实体 / 完结动作 → 必答"还有谁持有这个键、哪些决策态该退场"

删除操作影响的不只是被删实体——所有引用它的表和状态（勾选/标记/缓存/角标）都要过一遍；**完结动作同理**（归档/提交/评估完成/导出标记等使实体进入终态的操作）：

- 哪些表/前端状态持有它的键？（grep itemKey / 外键字段）
- 实体**删除或完结**后，同键的决策态（勾选/待办/进行中标记/角标计数）是否联动退场？
- **禁止用呈现层优先级当数据一致性手段**：当两个状态可能矛盾（如"已归档+勾选 true"），只调 UI 分支顺序让一方优先显示 = 用补丁掩盖矛盾——第 N 个消费方（计数/角标/导出）按另一态工作时矛盾必然漏出。消灭矛盾本身（完结联动清理），呈现顺序只是兜底不是修复。
- 谁负责联动清理？——**在仓库层/服务端做**（覆盖单删/批删/更新覆盖/完结全部入口），不放某个前端页面（漏入口）。
- 修复完结联动后，**存量矛盾对要一次性回填清理**——联动只对未来动作生效，不追溯历史数据。

先例：①删除产品部回溯归档条目未联动取消 decisions 勾选 → `postUseJiraRepository.clearTraceDecisionsForDeletedItem`；②归档（完结）不清勾选 → 非首次打开弹窗显示勾选态而非"已纳入"Tag（`archiveMany`/`upsertMany` 收尾联动 + #19 守卫）。

### 2. 写任何计数 / 角标 / 待办数 → 必写"何时归零"

提醒类数字必须先定义归零条件（通常 = 排除已完结条目），再写谓词：

- "已纳入/已处理/已完结的要不要排除？"——**默认排除**。
- 完结态实体常因"勾选保留、经办人另存"类设计把提醒计数永久占住。

**联动/兜底路径的 catch 必须外显 linkageError**（2026-11-10 测试复盘补充）：路由联动（删 A 清 B）或兜底逻辑的 catch 若只 log warn，联动失败在响应里表现为"成功但计数 0"——调用方无法区分"没有匹配"与"联动坏了"，故障穿上成功的外衣（先例：删回访联动解构 undefined 被吞成 cleared=0，定位绕三轮）。联动计数一律随响应返回 `linkageError` 字段并写入审计。

先例：①角标（待指定经办人数）把已归档行永久计入，存档提示误报；②删回访联动 catch 吞错 → 单删/批量删路由补 linkageError 外显。

### 3. 同一业务判定第 3 处出现 → 强制抽共享谓词

同一概念（已纳入 / 勾选 / 已归档…）多处各写一份内联过滤 = 判定漂移 = 必然出现"Tag 显示 12 条、筛选结果 0 条""行显示勾选、按钮说没勾"类矛盾：

- 新增任何呈现（Tag/筛选/计数/角标/按钮态）前先问：**这个概念已有哪些判定点？**
- 全部走同一判定函数或同一段派生数据；粒度差异（行级/组级）显式命名，不内联重写。

**已固化工具**：`node scripts/audit-shared-predicates.mjs`——扫描 src/ 直摸底层数据结构绕过共享谓词（isArchived / isDispatched / decisionOf）的代码，有绕过 exit 1，可接 CI。新抽共享谓词后在脚本 `SHARED_PREDICATES` 登记表中追加概念即可。

### 4. 方案级改动 → 必有"链路外的真实证据"

方案级（键结构 / 存储结构 / 口径 / 跨模块）改动，**测试全绿不算完成**——单测 fixture 常与真实链路形态不符（同一场事故：fixture 数组形态、链路 Set 形态，测试与实现共享同一错误假设，红绿证明对现实失效）：

- 至少一段真实证据：真实入参跑通完整调用链（node -e / 最小脚本）/ 生产形态数据 dump 对照 / 真机操作一次。
- 守卫测试锚定在**链路层**（走完整构建函数），不锚在纯函数层（纯函数守卫抓不到链路形态断裂）。

先例：`storyModel.test.js` 的"方案B 崩溃回归"用例——走完整 `buildPostUseStoryModel` 断言行键带月份段。

### 5. 给状态/动作定存储键（身份）→ 先答"它针对什么而存在"

动作类对象的身份 = **客体 + 时间界**。键缺时间界 = 把一次性事件建模成永久属性：

- "纳入回溯"针对的是"客户×产品×某月的发现"（一次性），不是"客户×产品"（永久实体）——键里缺月份导致跨月串扰。
- 拍板粒度类设计时，把隐含业务假设写成一句话请业务方确认（"处理一次是永久处理，还是按月独立？"）——假设没确认不算设计完成。
- 设计级修复（改键粒度/存储/口径）不能按普通 bug 修：全消费方清单 → 逐个验证 → 迁移方案 → 真实链路验证，风险高于修 bug。

### 6. 改共享解析层/共享工具函数 → 必答"谁在依赖这个返回形态"

共享层的返回形态就是契约。82742ef 教训：为 assistant 粘连场景给 `pickAssistantPayload` 加"取最后一个完整对象"启发式，静默剥掉了打标类消费方的 `{"results":[...]}` 批容器包装 → 6+ 个消费方批量模型答案整体丢失、回退本地还被误标 `journeySource:'llm'` → 红测试亮了 28 天无人问。

- 改共享函数返回形态前，grep 全部消费方，逐一回答"它期望什么形态"。
- 共享解析层的消费方场景不同（assistant 单对象 vs 打标批容器）→ 形态判定必须显式分支，不能一个启发式通吃。
- 改完必跑共享层的契约守卫测试（先例：llmClient.test.js 批容器契约 5 用例）；红着的历史测试不是"已知失败"，是**在报生产断裂**——先弄清它为什么红再决定动不动它。

### 7. 写"来源标注"字段（journeySource/source 类）→ 标注必须与事实同源

来源标注是下游口径的输入，失真标注 = 污染下游一切判定：

- 写标注时必答：这个值真的是这个来源产出的吗？回退/兜底路径产出的值必须标真实来源，不得沿用"主路径"的标注。
- 先例：模型答案未送达时 578 段用 UNKNOWN 占位 + 本地重匹配，362 行仍无条件标 'llm' → 下游 classifyPostUseJourney 把本地结果当"模型已判"→ 默认永不重试 → 待补计数静默漂移（修复 = llmVerdict 区分「模型真实判断」与「答案未送达回退」）。
- 消费口径字段前先问：**这个字段的生产方是否如实标注？** 数据真源失真时，下游一切口径修复都是沙上建塔。

## 排查约定

用户报"行为不对"时，先**分层归因**再定方案：同一现象可能来自"设计本来如此"（键粒度选择）也可能来自"实现没生效"（形态断裂）。**第一动作 = dump 实际数据形态**（存储的键/值长什么样），不要直接跳到设计层推方案。
另：**修口径类问题前先验证口径输入的真源**（如 journeySource 是否如实标注）——"分类没错但分到错误的类"和"分类对了但输入是假的"是两个完全不同的问题，修错方向会白走一轮。

### 8. 写"解释现象"的回复 → 必答"这个解释能被一条查询/一段代码指认吗"（11-10 部署修复复盘）

记忆里的设计语义不算证据。先例（最贵一课）：用户报"8 月弹窗 11 vs 库 10 差 1"，我凭记忆断言"周期包含语义"，方向对一半、机制全错——真因是旧格式无月份键跨月串扰；用户两次用业务常识质疑后回代码核实才见真。**解释未经验证就发给用户 = 用户成了唯一验证层。**

### 9. 加任何 CLI flag / 参数组合 → 必答全组合行为矩阵（11-10 部署修复复盘）

每个 flag 单独跑会动什么、不动什么，逐格写清（--fix 与 --mark-imported 单独跑的互斥行为、只读模式判定遗漏等三个 bug 皆源于 if 顺序碰运气）。**加 flag 未画"flag 组合 × 数据形态"矩阵 = 靠运气**。

### 10. 宣称"修复完成"前 → 必答"终态数字有实测证据吗"（11-10 部署修复复盘）

查询输出 / 截图 / 用户确认才算证据，只有推演不算——先例：UI 终态"10/10、5/5"当晚仍是推演未实测。

### 11. 写构造类测试用例 → 身份必须全库唯一（11-10 测试复盘×2）

同 describe 内用例共享测试库且顺序执行——前用例的数据残留会改变后用例前置（幂等用例先建同身份 → 删联动用例 created=[] → 404）；**beforeAll 共享数据也是"上一用例"**。用独立身份三元组或显式重建数据，不依赖用例执行顺序。

### 12. 注入环境状态构造测试前置 → 必先断言"状态真的成立"（11-18 复盘）

给测试/验证注入特定环境状态（目录/配置/开关）后，必须先断言该状态成立再跑被测行为——系统常有**自动补全/种子回填/自愈机制**让构造静默失效：

- 触发问题：写"兜底/未命中"路径测试时，先答"**系统有没有自动补回这个状态的手段**"（先例：注入仅 eip 目录想构造"云专线不在目录"，但 loadManagedProductCatalog 刷新时 ensureTargetProductsInCatalog 自动补回 dc 种子，断言失败一度误判为被测代码 bug）。
- 正确做法：兜底场景**优先用真实世界不存在的输入构造**（自定义产品名），不依赖"移除系统会自动补回的东西"。

### 13. 组合命令（mv/cp + git）→ 前半成功后半失败 = 半完成现场（11-18 复盘）

mv + git stash、cp + git 操作的组合命令，前半执行成功、后半（如 stash 对未追踪文件报 pathspec 错）失败时，现场处于半完成状态：

- 恢复现场前**先盘点**（ls 目标位置 / git status / stash list），不按"命令报错 = 没执行过"的直觉补操作（先例：mv 已搬走新文件，重跑时 mv 找不到源文件再报错，误以为文件丢失）。
- 组合命令拆独立步骤逐步执行逐步核对；排查用临时搬移法（mv 未追踪文件 + stash 追踪文件）时，收尾必须有**还原核对清单**：mv 回位 + stash pop + 关键文件内容 grep 复核 + 相关测试复跑。
- **升级（11-18 用户拍板）：HEAD 基线对照一律禁用 git stash，改用 worktree /tmp 对照法**（做法见 04-测试与验证约定 §4.1）——同日两次 stash 误打包用户进行中文件后立的硬规则；工作区有未提交改动时 stash 无"安全核对"可言，只有"核对过了"和"又没核对"两种状态。

### 14. 更换大模型配置 → 必答"全消费方的 token 预算与超时标定是否还成立"（11-18 报告文案复盘）

模型配置（llm_config_v1）换型号时，各调用点的 `max_tokens` / 超时都是按**旧模型的输出行为**标定的。推理型模型（reasoning 与正文共享 max_tokens 预算）会让这些标定整体失效——**思考吃光预算、正文 0 字或 JSON 截断，解析层报"不是合法 JSON"，且 temperature 重试必然同型连败**：

- 换模型前盘点全消费方预算（grep max_tokens）；预期输出量大、任务复杂的调用点（报告/诊断类）优先重标定。
- 先例①（patrol 线，61f8712）：共享默认 2048 下复杂组 reasoning=3748 吃光预算 → 正文 0 字，预算 8192 + 超时 120s 联动放宽。
- 先例②（报告 V2 文案，11-18）：`max_tokens=4000` 按非推理模型时代标定，生产规模（99 产品）reasoning=4000 吃光预算、text=0 → 两种"不是合法 JSON"报错（思考草稿被当正文 / 截断 JSON 被解析层救出小对象）；修复 = 预算梯度 [16000, 24000] + finish_reason=length 检查重试。
- **红着的守卫测试是在报生产断裂**：batchKeysGuard 在 c49cfe4 上线新版月季报当天就红了（prompt 承诺 focus/products/todos 容器键未入白名单），红了一天无人理——真实链路里完整 JSON 被剥成最后一个子对象正是这颗雷引爆。

### 15. 平移含状态步进的核心算法 → 抽共享函数优先，重抄必逐行 diff（11-23 复盘）

把逻辑从一个宿主"平移"到另一个（弹窗→页面、tab→tab）时，含**状态步进/分组/索引**的核心算法（分组循环、指针步进、归并标记）禁止凭理解重抄：

- **逻辑等价性差异是单测/esbuild 的天然盲区**：`i += 1` vs `i = j` 在单元素组上行为完全一致、多元素组才分叉——测试全绿不证明平移等价（先例 11-23：清单 tab 平移弹窗分组循环，步进抄错 → rowSpan:0 吞行失效、合并组整行列错位，真机才暴露）。
- 正确做法优先级：**能抽共享函数/共享模块就抽**（单一真源），确需重抄（如 JSX 内联闭包）→ 逐行 diff 原版，特别核对循环边界、步进语句、分组标记赋值三处。
- 交付时风险标记要指向**看得到的具体交互**，不能替代逐行核对——先例：标记了"rowSpan × 列宽拖拽"，真凶是手抄步进，标记方向反而误导排障。

### 16. 写计数类 UI（`名称 (n)` 下拉/角标/汇总数）→ 必答"n 的统计对象 = 宿主实际展示对象？"（11-23 复盘）

同款 UI 形态在不同宿主里统计语义可能不同——抄实现必抄语义，否则计数与展示内容脱节：

- 先例 11-23：清单 tab 产品下拉抄工作台的"scopedItems 按产品计数"，但工作台语义 = 原始评价记录数，清单 tab 语义 = buildPostUseCallbackLists 过滤后的可见行数——下拉显示 n 大于 tab 实际行数。
- 触发问题清单：这个 UI 的宿主显示的是什么（原始记录/过滤后行/聚合组）？count 的数据源与显示对象是同一个吗？
- 有多道内部过滤的构建函数（buildXxx 类），计数必须从**构建产出**聚合计数，不从输入记录计。

### 17. API 响应白名单裁字段 → 判别字段（kind/type/source）默认透传（11-23 复盘）

API `.map()` 白名单挑字段在"当初够用"的时点是对的决定，但**裁掉判别字段是单向门**——消费方后来需要区分形态时（option vs quote、枚举 vs 自由文本），前端只能硬编码猜测标签：

- 先例 11-23：`/source-issues` 白名单裁掉 `kind` → 前端把选项类反馈（"功能缺失/不完善"）硬标"原话："，用户核实才发现误标。
- 规则：响应映射裁字段时，**kind/type/来源判别类字段默认透传**；裁掉必须在路由注释登记"裁了什么、为什么"；下游要区分展示形态时，第一反应查上游有没有这个字段，不是前端写死。

### 18. 修定位/渲染异常类 bug（popup 漂移/sticky 叠压/层级错乱）→ 必答"同类实例全量扫了吗"（11-23 复盘）

修复宣布完成前，grep 全部 sticky/fixed/吸顶容器内的同类组件实例——报障点修复 ≠ 类别清零：

- 先例 11-23：下拉漂移用户报 2 处、修 2 处宣布完事；二轮全量扫才发现同一 tab 还有 2 个 Select 漏网（含更隐蔽的 `fixed: 'right'` 表格列内 Select），其中一个是自己前一天刚写的。
- 修复动作必须包含**类别化步骤**：确定 bug 的技术根因（如"sticky 容器内 Select 缺 getPopupContainer"）→ 按根因特征 grep 全部同类实例（`<Select` in sticky/fixed 环境）逐个核对，不依赖报障清单。
- 同根因修复后，新增同类组件时的守卫（如源码断言"sticky 环境内 Select 必带 getPopupContainer"）比逐处修复更防回潮。

### 19. 新建 server/ 侧文件 → 落盘后必跑一次真实模块加载，import 从别处复制时逐条对照目录深度（11-23 深夜复盘）

- 先例 11-23：`issueLinkAutoJudge.js` 新建时误抄 `routes/` 目录文件的 import 深度（`../` 应为 `./`），本地 vitest 全绿（测试没走模块运行时加载路径的部署形态），部署环境 LLM 判定全链瘫痪，用户报障两轮才定位。
- 动作：新文件写完立即 `node --input-type=module -e "import('<绝对路径>')"` 验证加载；复制 import 块时意识到"正确性真值条件含文件自身位置"，逐条目测基准目录。
- 守卫：`server/postUseErrorChainGuard.test.js`（server 根生产文件相对 import 逐条可达扫描，红绿自证）。

### 20. 写任何 LLM 响应消费代码 → 必先 grep getLlmCompletionText，禁止自写 content 提取（11-23 深夜复盘）

- 先例 11-23：verdict 解析器自写简化版直接读 `message.content`——推理型模型 content 可能为数组形态（平台 11-18 已为此付出排查成本并沉淀共享提取器），自写版在部署环境报"无法解析"。上午同型没翻车是 mock 恰好喂字符串——测试与实现共享同一错误假设。
- 动作：任何"从 LLM 响应取正文"的代码，先查 `src/lib/llmClient.js` 的 `getLlmCompletionText`；平台解析器存在即用。测试 fixture 必须含数组形态用例（防 mock 与实现共谋）。
- 守卫：同上（issueLinkVerdict 源码断言必含 getLlmCompletionText、禁直读 choices[0].message.content）。

### 21. 改任何 API 响应形态 → 影响面搜索必含前端两层（src/lib 客户端函数 + src/components 直读点）（11-23 深夜复盘）

- 先例 11-23：三触发点重构把 `/links/auto` 响应从 `verdicts` 数组改为计数对象，只 grep 了服务端消费方——前端 Linker 组件仍读 `result.verdicts`，判定成功但提示恒"0 个候选"。**API 响应形态不是服务端内部实现，是前后端共享契约**。
- 动作：改响应字段时，grep 该端点路径字符串定位 `src/lib` 客户端函数，再 grep 客户端返回值在 `src/components` 的直读字段；契约测试断言服务端响应字段与前端消费字段对拍。
- 守卫：同上（/links/auto 前后端契约对拍：服务端必含 saved/skippedManual/message，前端禁读 verdicts）。

### 22. "接数据"类改动上线前 → 用部署环境真实数据形态驱动一遍消费链（11-23 深夜复盘）

- 先例 11-23：溯源文本消费优先级 `recommendedReason || progress`——本地库 4 条溯源 progress 全空，消费顺序缺陷完全不可见；部署环境用户把人工结论填在 progress（抽屉"回溯结果"必填字段），机器模板句永远压住人工结论，用户报"溯源未生效"。
- 动作：字段取值顺序/优先级类改动，验证数据必须来自真实使用形态（部署环境 dump 或字段填写场景确认），本地测试库数据形态可能从未覆盖真实用法。

### 23. 修复"完成"判定 = 部署环境验证过，而非"改完+测试绿"（11-23 深夜复盘）

- 先例 11-23：用户连续报障四轮，其中恒 0 提示、解析失败都是**修复上一个问题时顺手制造的新问题**——修复流水线没有"部署验证"闸门，缺陷在流水线排队向下传递；每轮修复只到"测试绿"就交付。
- 动作：多修复连续交付时，每轮修复的验证清单必含"部署环境可验证点"（哪怕标记为待部署后确认）；一轮修复引入的响应形态/接口变化，当轮内自查全部消费方（见规则 21）。
- 关联：规则 10（宣称修复完成前终态数字实测）、规则 1（真实链路验证）。

### 24. 写任何「组件 A → 组件 B/裸元素」的替换（尤其批量）→ 必答"A 身上有哪些 B 没有的能力 props"（11-25 万投比 tab 复盘）

先例（72 天才被用户发现）：c5e92f3 卡片规范重构把 antd Card 换成 div.page-card，Card 挂着的 `tabList/activeTabKey/onTabChange` 三个行为 props 在 div 上无处可挂被静默丢弃——但 tabList 的 useMemo、activeProductKey 的 useState 全都完好存活，只是不再被渲染消费，typecheck/测试天然失明。**Card 是带行为能力的复合组件（页签路由/extra 工具区/hoverable/styles），不是视觉皮肤**。

- 动作：替换前逐个列出 A 的全部 props，标记"B 有没有等价物"——没有的必须给迁移方案（如 Card tabList → antd Tabs items）或显式声明放弃并写进提交说明；
- **批量重构 ≥5 文件 → 必做行为等价性验收**：三版对比法（重构前 blob / 重构后 blob / 当前 blob，提取中文文案+函数名+交互标识符 token，`(前-后)-现` 即真丢失），候选再逐个上下文人工定性（等价迁移/有意重设计/纯视觉/真丢失）；
- **低频关键能力（管理员设置/外部依赖开关类）上线时必配真渲染守卫**，不等用户当探测器；
- 守卫：`src/lib/deadHookBindingGuard.test.js`（hooks 绑定文件内零消费即红——重构吞掉消费端后声明仍在的形态，c5e92f3 当天形态已内嵌红证）。

### 25. hooks 绑定声明零消费 ≠ 无害垃圾 → 当成"消费端被吞"的信号排查（11-25 万投比 tab 复盘）

死代码扫描守卫报红时，禁止直接加豁免了事——**"绑定活着、消费死了"正是重构事故的残骸形态**：

- 先 git log/blame 定性：声明的引入提交里它被谁消费？消费端何时被谁删掉（是功能迁移有等价物，还是被吞）？
- 真孤儿（有等价机制）才进豁免清单，豁免注释必须写清"等价物在哪、何时可删"；消费端被吞的当场补回（先例：tabList→Tabs）。
- 现存豁免：PostUseHtmlReport 六处（11-20 V1 下线孤儿，V2 等价机制在）、InsightsContext reprocessAllTagsCore（批量任务服务端化后绕过）。
