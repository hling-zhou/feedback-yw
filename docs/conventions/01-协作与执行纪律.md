# 01 · 协作与执行纪律

> 适用对象：人 + AI 辅助开发会话。整理自项目工作记忆与用户全局约定，出处日期随条目标注。

## 1. 执行前对齐三样（2026-09 起持续生效）

接到需求先简要说明理解和做法。需求明确时继续执行；只有指代、业务口径、范围或高影响连锁需要用户决策时，才暂停依赖该决策的部分并澄清：

1. **大白话复述需求**：用自己的话把需求讲一遍；
2. **具体做什么**：说明已知的文件/模块、改法与验证方式；未知部分先调查再明确；
3. **关键假设与边界**：只说明会影响结果或范围的假设与边界。

有歧义时先确认指代对象，同时可继续不依赖该答案的调查。**需求词指代不明时必须确认指代对象**——先例（11-10）：「其他列原样显示」中的"其他列"，我按"当时的存量列集"惯性执行，用户原意是"导入模板列"，整列返工。

## 2. 需求变更与记忆冲突

- 改动会触发"重新归类/重跑全量"类连锁时，先说清差异与影响面再动手。
- 用户反馈与既有约定/记忆冲突时，**以用户最新指令为准**，指出需同步的条款，不沿用旧约定硬顶。文档按本目录 README 的授权规则更新；工作记忆仅在用户明确要求且工具允许时更新。

## 3. Edit 工具锚点纪律（11-09 沉淀，单日三次同型失误教训）

Edit 工具是**替换语义，不是插入语义**：

- 以函数声明行/注释块做锚点时，new_string **必须完整回写锚点行**，否则函数头被吞、函数体悬空。
- **触发规则：每次以声明行做锚点的 Edit，落盘后立即 grep 锚点函数名复核存在**。
- 大跨度 JSX 结构改写，紧跟 esbuild 语法验证（esbuild transform 仅证明语法，不证明行为）。
- JSX 条件包裹大块时，闭合顺序 = 先 `</div>` 闭元素，再 `)}` 闭表达式——写反过一次，esbuild 报 Expected ")"。

## 4. 同文件多处编辑串行（10-25 实测教训）

同一文件的多处 Edit **不要在同一条消息里并行发**——实测存在写覆盖竞态（同文件两处编辑一处被吞，行为不稳定）。多处改动分条消息顺序发，每处落盘后用 Read/Grep 复核再进行下一步。

## 5. 排查与调查纪律

- **调查禁循环论证（11-09）**：查 bug 的数据形态时，禁止沿用被调查代码的字段路径写 SQL/查询——查询会继承 bug 的心智模型，查出的"异常"只是 bug 读取方式的镜像。先查 types.js / schema 的字段语义，再写查询。
- **写 key/字符串解析函数 → 必先打开生产方代码逐段对照格式**，禁止凭样例直觉猜段位。先例：productNameFromItemKey 第一版凭直觉把月份段当产品名。
- **服务未运行时报告的现象 ≠ 当前代码+数据的产出**（11-09）：先 lsof / health 探测进程在不在；不在则现象来自旧进程/旧数据窗口，排查方向转向"构造最小复现验证当前代码"。
- **解释现象前必答"这个解释能被一条查询/一段代码指认吗"**（11-10 最贵一课）：记忆里的设计语义不算证据——曾凭记忆向用户解释"差 1 条是周期包含语义"，真根因是旧格式键串扰；解释未经验证就发出，用户成了唯一验证层。
- **加 CLI flag 必答全组合行为矩阵**（11-10）：每个 flag 单独跑会动什么、不动什么，不靠 if 顺序碰运气。
- **宣称"修复完成"前必答"终态数字有实测证据吗"**（11-10）：查询输出/截图/用户确认才算，只有推演不算。
- **E2E 失败第一步 = 打印响应原文**；排查前先确认验证脚本自身的现场（挂了哪些路由/哪个库/哪个用户）——验证工具自身的故障会伪装成被测系统的 bug（11-10）。
- **排查现象先分层归因**：同一现象可能来自"设计本来如此"也可能来自"实现没生效"——第一动作 = dump 实际数据形态，不要直接跳到设计层推方案。
- **多模式 bash grep 不可靠**（11-07 两度实测）：`grep "a\|b\|c"` 多次哑火/误报——源码扫描/输出过滤一律用 ripgrep 或单模式多次 grep；多模式 grep 得出的阴性结论不可采信。

## 6. AI 会话工作方式（供 AI 协作者）

- 本地若有 `.workbuddy/memory/`（不入库），可查过程记录；新协作者无需依赖它。**本目录（docs/conventions/）是入库版约定**，约定变更按本目录 README 的授权规则登记。
- 交付说明里显式声明"已/未真机确认"（渲染测试对跨文件视觉一致性零拦截，见页面UI规范 §5）。
- 执行任务后复述关键步骤与核心逻辑，让用户确认理解一致（2026-09-11 用户约定）。

## 7. 工程复盘的项目结论落点（2026-11-12）

复盘时核实事实、错误假设、系统性诱因和验证盲区，再按复发风险选择防复发措施；不要求每次都新增记忆、文档和代码守卫。本目录只维护经确认持续适用于本项目的结论：

- 开发动作触发的规则，登记在 [防缺陷触发规则.md](防缺陷触发规则.md)。
- 数据口径和设计决定，分别登记在 [03-数据真源与口径.md](03-数据真源与口径.md)、[05-设计拍板与已知坑.md](05-设计拍板与已知坑.md)。
- 验证方式和 UI 约定，分别登记在 [04-测试与验证约定.md](04-测试与验证约定.md)、[页面UI规范.md](页面UI规范.md)。
- 值得自动拦截的复发风险，按具体结论增加测试或审计脚本，并在本目录 README 登记；只有接入必经检查流程，才称为强制拦截。
