# 04 · 测试与验证约定

> 改完代码后、交付声明前必读。出处日期随条目标注。

## 1. 测试执行三要素

- 修改后**只跑受影响的 vitest 子集**，不跑全量；E2E 需用户明确指令。
- vitest 临时 config 真源 = `git show e51ddce:vitest.tmp.config.mjs`，跑前恢复（仓库内 vitest.tmp.config.mjs 是临时产物）。
- 运行环境三要素（沙箱/代理坑，10-25 已修）：**非沙箱执行 + `env -u NODE_OPTIONS` + 装包用 npmmirror 镜像**。
- 纯 lib 单测秒级；SSR renderToStaticMarkup 测试必须 node 环境；重型 import 放文件顶层。

## 2. 真实链路验证纪律（11-06 沉淀，"单测全绿"不是完成标准）

方案级/功能级改动，必须用 node -e / 最小可运行脚本拼**真实入参**跑**完整调用链**：

- **深因：fixture 常是从实现代码反推的**——测试与实现共享同一心智模型，同一个错误假设（Set vs Array、分页后 index、运行时注入字段）会同时污染两者；红绿只证明测试对代码敏感，不证明对现实敏感。
- 独立验证必须来自心智模型之外：真实数据 dump / 生产形态抽样 / 真机操作。
- 守卫测试锚定在**链路层**（走完整构建函数），不锚在纯函数层——纯函数守卫抓不到链路形态断裂。先例：storyModel.test.js "方案B 崩溃回归"用例走完整 buildPostUseStoryModel。
- 先例（11-11）：列宽拖拽改动用"临时库+种子目录→ingestPatrolRequests→compressPatrolDay→断言"的真实链路验证 assignee 默认值，用户要求"不要假绿"。

## 3. 测试编写约定

- **构造型用例身份必须全库唯一**（11-10 教训×2）：同 describe 内用例共享测试库且顺序执行，前用例数据残留会改变后用例前置——beforeAll 共享数据也是"上一用例"；用独立身份三元组或显式重建，不依赖用例执行顺序。
- **renderToStaticMarkup 不跑 useEffect**：异步加载面板的渲染测试只能断言空态 + 纯逻辑映射（columns 列头定义），不能断言加载后内容/数据行。
- **vi.useFakeTimers + Promise setTimeout 组合 = 假计时器下 Promise 永不 resolve** → 进程挂死（11-09 实测被 SIGKILL）；jsdom 组件测试用真实计时器微等待。
- node 测试环境无 `globalThis.location`——同源校验类逻辑以 `doc.baseURI` 推 origin（先例：versionProbe 假绿风险）。
- 插新函数前 grep 精确函数名，防同文件重复声明。

## 4. 守卫测试与红绿证明

- **新增断言/白名单/豁免时，必须注入反向 bug 验证能红**（红绿证明）——豁免 ≠ 扫描盲区。
- **红着的历史测试不是"已知失败"，是在报生产断裂**——先弄清它为什么红再决定动不动它。先例：Import.customerVisit.layout 红着是锚点文案漂移，改锚点前先 stash 对照证明 HEAD 也红。
- 守卫测试自身必须红绿证明（先例：受控 Tabs 双保险守卫）。
- **红绿证明的临时回退，禁止对未提交改动用 `git checkout -- <file>`**（11-09 实测：整文件不可逆抹掉）——用精确字符串替换 + 手动恢复，或先 cp 备份。

## 5. typecheck 纪律

- 触碰文件 TS2304/TS2307/TS2552 **零新增**；与历史基线比对（`/tmp/tsc-*.txt`），注意行号归一化后 diff——属性顺序变化是文本噪音。
- **给既有函数加 JSDoc 标注会把隐式 any 参数拉进检查面**，凭空多出一片 TS2339/TS8032——加标注前想清楚（11-09/11-10 两次再现）。JSDoc `@param {object} props` 收窄会触发 TS2339，宽标 `any` 是既有欠账的务实处理。

## 6. 验证与交付声明

- **esbuild transform 仅证明语法**；改组件必跑真渲染测试（renderToStaticMarkup）。
- 无渲染覆盖的组件交互（弹窗预填、拖拽手感等）→ 交付说明里**显式声明"需真机确认"**。
- UI 结构改动必须真机目检——渲染测试/typecheck 对"跨文件视觉一致性"零拦截（三反模式代码 130/130 全绿的先例）。
- **宣称"修复完成"前必答"终态数字有实测证据吗"**（查询输出/截图/用户确认），只有推演不算完成（11-10）。

## 7. E2E 排查

- E2E 失败第一步 = **打印响应原文**，不要直接下结论。
- 排查前先确认验证脚本自身的现场：挂了哪些路由/哪个库/哪个用户——验证工具自身的故障会伪装成被测系统的 bug（11-10：冒烟脚本没挂 jira 路由 → 标记 404 → 误怀疑 deleteByIdentity）。
- E2E 需要用户明确指令才跑（见 §1）。
