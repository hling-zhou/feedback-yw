# 行动建议机制 · 完整方案（定稿 · 待确认）

> 整理自 2026-09-08 多轮对齐。设计目标：**用户自定义时间周期 → 分产品生成行动建议 → 横向跨产品发现共性**；顶层规则先定好、机制能自适配产品、分析结果自动复核、采用**分离控制**（复核与调整均为独立第三方）、并保留**人在回路**。

---

## 一、需求对照

| 最初要求 | 落地方式 |
|---|---|
| 用户自定义时间周期 | 月对模型（基线月+当前月）；`DATA_XLSX` 换数据源、`PRODUCTS` 换产品作用域 |
| 分产品生成行动建议 | 每产品独立 5 层信号 + 一页纸备忘录（真声 + 分析层双层） |
| 横向跨产品发现共性 | `export-cause-crossprod`：SUPER 9 共性根因轴热力图 |
| 顶层规则先定义好 | 阈值公式 + 5 层框架 + 字段出处红线 = **人类固定基线、永不被自动改写**；`CAUSE_TAX_MAP` 的 **in-code 常量本体**永不被自动改写（Fixer 只叠 overrides 增量），但其**生效家族集已放开为机器自适应 + 人兜底审核**（见第四节） |
| 能自适配产品 | 家族级**机器自适应**（见四）+ `autoSplit`（L2 细分）+ 相对阈值随 T/B 缩放 |
| 分析结果自动复核 | **第三方门禁**独立重算 + 完整性交叉校验 + **全量分类准确性校验** |
| 分离控制；复核和调整都是第三方 | Producer ≠ Gate ≠ Fixer，三者独立进程、互不信任对方产物 |
| 保留人在回路 | 派生草稿人工注册、发布前过目变更日志、`needs_human` 升级、准确性抽样由人兜底复核 |

## 二、分离控制三方架构

```
   Producer ──dist 产物──▶ Gate(第三方复核) ──失败报告──▶ Fixer(第三方修复)
   (写·不自判)              (独立重算+全量准确性)            (外科式改分类法)
        ▲                        │  ▲                          │ overrides 增量
        └──────── run-loop 编排器（薄壳·只 spawn·不信任任一方）┘
```

| 角色 | 文件 | 职责 | 是否自判 |
|---|---|---|---|
| 写 Producer | `validate-action-recs.cjs --emit` | 跑分类，只写 `dist/` 产物（含每工单 status/文本），**不自判** | 否 |
| 复核 Gate（第三方） | `gate-check.cjs` | 独立重算未归类/待确认率 + 完整性交叉校验 + **全量分类准确性校验** | 独立仲裁 |
| 修 Fixer（第三方） | `fix-classification.cjs` | 独立读失败报告+证据，外科式改分类法，只写 `overrides` 增量 + `docs/变更日志` | 改后须再过 Gate |
| 编排器 | `run-loop.cjs` | 依次 spawn 三者，有界 **5 轮**，过即发、卡住升级人工 | 薄壳 |

**独立性保证**：三者均独立子进程；Gate 不调分类引擎、不读 records、不采信 Producer 自报聚合数，用 `evidence-rows` 逐工单 status 重算；Fixer 只读 gate-report + evidence + taxonomy-current，只写 overrides 增量与 changelog。

## 三、顶层规则（人类固定基线 · 永不被自动改写）

1. **聚类主键** = 原因优先 + 痛点兜底（原因命中可信度高；痛点命中 >50% 的家族对外标"根因待人工确认"）。
2. **原因家族分类法 `CAUSE_TAX_MAP`**：人类手写（EIP 16 家族 / 其余三产品已校准），是"可监督、非黑箱"的根。**两层口径**：① **in-code 常量本体**——永不被自动改写（Fixer 只叠 `overrides` 增量，删增量即回滚）；② **生效分类法（baseline + overrides）**——家族级已放开为**机器自适应 + 人兜底审核**（新家族 / 重划边界由 Fixer 提草稿进 `derived`，人签核才转永久基线）。
3. **阈值相对化公式**（按产品体量 T、投诉基线 B 动态算）：
   `H=min(100,max(17%,1.5×B))` · `S=max(10,round(0.10×T))` · `L=max(3,min(10,round(0.01×T)))` · `Δ=clamp(round(0.05×T),3,12)`
4. **5 层信号框架**（信号驱动，非固定模板）：长期结构性 + 本月异动 + 小而锐 + 常规迭代池 + 平稳长尾 + 横切项单列。
5. **字段出处红线（含"已办去重"护栏）**：
   - 真客户原声 = `客户请求内容 / 受理内容 / 处理意见`（唯一可被引用的客户侧原话）
   - 〔痛点摘要〕= `需求痛点`（分析层）；〔复核根因〕= `问题原因`（分析层）
   - `确立举措` = 工单级"已办事实"文本（**非建议、非真声**，是下游动作事实）。⚠️ **它只是逐单佐证，不是"状态/是否纳入优化"的权威来源**。
   - **"是否纳入优化 + 状态"的权威来源 = 举措库关联（带状态的 action item 仓储），与现有「专题分析」模块同源**：`src/lib/topicAnalysis/collectEvidence.js` 已为每个问题簇统计 `inventory`——`open`（开放/进行中）/ `done`（已完成·仅代表动作落地，**≠ 已根治**）/ `stopped`（已停摆）；`buildTopicAnalysisChapters.js` 据此标 **"先跟进已有举措 · 避免重复立项"**，`buildDecision.js` 据此判 `跟进` 或 `换方向评审`。**action-recs 的收敛环节应直接复用这套 inventory 逻辑，不另造轮子**，仅当问题簇无关联举措时才作为新优化建议纳入。⚠️ **"举措完成"与"问题根治"是两件事**：`done` 只证明动作做了，根治需效果验证/复发观测信号才能下结论。
   - **去重 / 闭环护栏（在"行动建议收敛环节 / Producer 写阶段"落地）**：对每个问题簇查举措库关联 → ① `open` 举措存在→标"已确立·先跟进效果验证 / 避免重复立项"，**不纳入新优化**；② `done`（已完成·仅动作落地）→标"已落地·待效果验证（**≠ 已根治**）"，需观察复发/验收效果，不自动判根治，进"已办待验证"池而非新优化；③ `stopped`→标"已停摆·升级换方向"；④ 无关联举措→纳入新优化建议。⚠️ **"根治"不能由举措状态推导**，必须经效果验证/复发观测信号确认（如该类工单量环比持续下降、同类投诉不再出现）；工单 `确立举措` 字段仅作"动作确实落地过"的佐证。
   - `产品技术优化` = 收敛素材（LLM 自动产出，**严禁当建议**，仅供人工收敛参考）
   - ⚠️ **现状缺口（方案补齐项）**：主链路 `validate-action-recs.cjs` **未接入举措库关联 / 未消费 `确立举措` 佐证**（后者仅被独立的 `promote-established-actions-to-playbook.mjs` 沉淀为 playbook）。需在 Producer 收敛环节接入举措库 inventory 逻辑 + 工单 `确立举措` 佐证（见第十节待办④）。相邻字段（`排期`/`未完成待办`/`服务流程改进`/`产品组优化建议`/`设计师优化建议`）**不在本方案治理范围**，仅管 `确立举措` 一项。

## 四、自适配产品（家族级放开 + 人兜底审核）

| 自适配发生在哪 | 是否碰 CAUSE_TAX_MAP | 终局 |
|---|---|---|
| ① 家族级**机器自适应**（新家族/重划边界） | 不回写；进 `overrides` 标 `derived` | **人兜底审核**：changelog 供复核，注册清单需人签核才转永久基线，否则停 `derived`，人可否决回滚 |
| ② L2 子议题自动细分（autoSplit） | 不碰，只提议 | 人工确认后写进 TAX 成常驻 |
| ③ 相对阈值随 T/B 缩放 | 不碰（公式固定，数值每期算） | 公式人类定、数值数据驱动 |
| ④ Fixer 的 overrides | 不碰，只叠增量 | 机器增量→发布前人工过目 changelog |

**家族级放开的三道护栏（防漂移）**：① 强证据门槛（成簇未归类/弱归类工单支撑 + 与现有家族区分度，靠全量准确性门禁判定）；② 发布前过全量准确性门禁；③ 人兜底签核。

## 五、时间周期

- 当前为**月对模型**：基线月 + 当前月，`环比(MoM)` 由 jul→aug 算得，"本月异动"层（双判据 `|环比%|≥50% 且 |Δ绝对|≥10单`）依赖此。
- 参数化：`DATA_XLSX=<path>` 换数据源/月份；`PRODUCTS=<逗号列表|*>` 换产品作用域。
- **8 月试跑**：采用 **(A) 7+8 月**（8 月=当前月、7 月=环比基线）→ 异动信号可触发、门禁≥2 月检查通过，无需改代码。（B）纯单月 8 月快照需小改（加 `MONTHS` 参数 + 放宽≥2月要求 + 关闭异动层）。

## 六、自动复核（第三方门禁 · 现状 + 新增）

**现状检查（保留）**：解析完整性、未归类率(<5%)、待确认率(<20%)、小而锐 n≥3、横切单列、出处标注、重算数=自报数一致性交叉校验。

**解析完整性检查重映射（部署后为 records 表）**：
- `sheet维度` → `数据分区(import_batch_id)存在`（xlsx 无 sheet 概念）
- `来源类型` → 若 records 带来源类型字段则保留，否则并入分区检查
- `月份 / 工单号 / 产品名称` → 保留（改从 records 字段取）
- 即**不在 xlsx 上跑**，按 records 世界等价物重映射。

**新增：分类准确性检查（全量）**——直击"分到对不对"的盲点：
1. **独立再分类校验（全量）**：门禁对**每一张**工单独立重跑轻量打分，断言 Producer 指派家族 = 门禁 top-1（或 top-k 且领先 #2 有 margin）；不一致 → 误归属 FAIL，列工单号+双方判定。
2. **术语一致性（防泛化）**：每家族统计其归属工单含"非泛义判别词"的占比；大量工单只命中泛词（裸"中断/配额/子网"）而无专属词 → 标"泛词误吸嫌疑"，进抽样复核清单。
3. **负向/排除校验**：归属某家族的工单不应同时强烈命中该家族排除模式（如"流程中断"不应进"网络链路质量"）。
4. **漂移护栏**：overrides 前后对比各家族体量分布，异常剧变 → 告警（防 Fixer 改一处把整族带偏）。

## 七、自动调整（第三方修复）

**可修策略（第三方有权修订）**：
- A `add_coverage`：未归类率 FAIL → 在未归类工单挖高频未覆盖短语补为新子议题。
- B `restrict_term`：待确认率 FAIL → 泛词收窄表（仅当证据显示跨家族歧义）。
- C **准确性修订**：全量再分类 FAIL → 收窄正则 / 补排除 / 调分类边界，修正误归属与泛词误吸。

**铁律**：A/B/C 均**只能收紧 / 补排除 / 升人工，不能放宽放水**；任何修订后必须再过门禁。其余（派生草稿 / 阈值 / 横切 / 出处 / 解析 / 证据不足）→ 标 `needs_human` 升级人工。每轮改动全落 `docs/变更日志`（before/after + 门禁信号 + 证据工单）。

## 八、人在回路

- 派生草稿 / 新家族**必须人工注册签核**才转永久基线（人只做兜底审核）。
- 发布前 `run-loop` 提示：`docs/变更日志-*` 中的机器改动需人工过目（可审计、可回滚）。
- 准确性抽样复核清单由人兜底确认。
- `needs_human`、数据级/完整性失败一律升级人工，不静默放过。
- 一页纸备忘录本身供人做下一步决策。

## 十、8 月试跑计划（**待你确认 OK 后执行**）

- **命令**：`node scripts/run-loop.cjs`（默认作用域=4 curated 产品，选项 A：7+8 月）。
- **预期产物**：四产品 `行动建议-{产品}-验证.md` + `-module.html`、跨产品 `四产品-原因家族-横向对照.html`、`dist/gate-report.json`、`docs/变更日志-*.md`。
- **已知要点（诚实）**：默认作用域 4 产品基线很稳，试跑**大概率一轮 30/30 通过、Fixer 不触发**——即"自动调整"在此试跑中不会实际动作（自愈能力已在隔离沙箱用合成场景验证过 14.3%→0%）。若你想在真实 4 产品上亲眼看到 Fixer 动作，可先注入一处可控缺陷再走闭环。
- **待落地代码改动**（方案定稿后才动）：① 门禁加"分类准确性（全量）"4 项检查；② 解析完整性检查重映射为 records 世界；③ Fixer 增加 C 类准确性修订策略；④ 家族级自适应进 `derived` + 人兜底签核流程；⑤ Producer 收敛环节接入**举措库关联 inventory 逻辑**（复用 `topicAnalysis/collectEvidence.js` 的 open/done/stopped 判定，输出"是否纳入优化 + 状态"），并叠加工单 `确立举措` 作"动作已落地"佐证——实现"去重·闭环护栏"（有 open 举措→标"先跟进·避免重复立项"、**done→"已落地·待效果验证（≠根治）"**、stopped→"换方向升级"、无关联→纳入新优化建议）。⚠️ **根治判定必须基于效果验证/复发观测信号，不能由举措 `done` 状态直接推出**。
- **前端查看器（(B) 方案：让用户兜底审核落到 UI）**：Fixer 在写 MD 之余**追加写 `dist/changelog-feed.json`**（累积数组、每轮一项，非覆盖，含：产品/时间/动作类型/before-after/触发的门禁信号/证据工单/状态）；server `routes/storage.js` 新增只读 `GET /api/storage/changelog-feed`（`preHandler: requirePermission('view')`，文件不存在返回 `[]`，复用现有 storage 路由模式）；**前端落点 = 洞察工作台首页行动建议模块区**（用户指定）：在 `src/pages/InsightWorkbench.jsx` → `src/components/workbench/OverviewTab.jsx`（第 140 行 `<PlanningRecommendationsPanel>` 所在概览区）内，于行动建议面板同级/底部新增 `src/components/workbench/LoopChangelogPanel.jsx`（只读列表 + 展开看 before/after + 门禁信号 + 证据工单），读 `/api/storage/changelog-feed`。**落点理由**：用户指定"洞察工作台首页呈现行动建议，将人兜底审核也放过来"；`PlanningRecommendationsPanel` 即现有"行动建议"模块（`PLANNING_RECOMMENDATIONS_PANEL_TITLE='行动建议'`），新设计的 action-recs 产物与闭环修订查看器都挂此区域，人看建议与看机器修订在同一屏。
